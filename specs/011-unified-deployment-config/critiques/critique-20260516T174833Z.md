## Executive Summary

The spec is well-bounded and the plan is technically sound; the dual-lens review surfaced **five must-address gaps** that span product and engineering. All five are addressable by additive edits to `spec.md` / `plan.md` and do not require revisiting scope or architecture. After remediation the feature is ready for `/speckit-tasks`.

**Verdict**: ⚠️ PROCEED WITH UPDATES — must-address items resolved inline below.

## Product Lens Findings

### 3a · Problem Validation

No findings. Problem statement is concrete; scope boundaries are explicit; alternative paths (SDK-only) are acknowledged.

### 3b · User Value Assessment

**P-001 (Recommendation)** — User stories cover read, edit, high-impact-change, and Component Overrides, but there is no story for a viewer **without edit permission**. Currently the spec implicitly assumes "viewer = editor". If the project's auth model has a read-only viewer role (it does — see `dev/guides/users-and-groups.md`), the Edit configuration button needs to be gated, and the empty drawer state for non-editors needs to be defined.

**P-002 (Recommendation)** — No user story covers the **error-recovery** flow when Apply fails mid-rollout. FR-025 captures the dialog behaviour ("stay open, surface error, preserve changes for retry") but no acceptance scenario demonstrates the operator path.

### 3c · Alternative Approaches

No findings. Plan correctly reuses TanStack Form / Radix and the existing `deploymentConfigToInput()` helper rather than reinventing.

### 3d · Edge Cases & UX

**P-003 (🎯 Must-Address)** — Accessibility is unaddressed. The drawer involves focus trapping, keyboard navigation between sections, an off-canvas form that screen readers must announce, dynamic "changed" pills and amber borders that need text-equivalent state, and a confirmation modal with a primary destructive button. None of this is in the spec.
**Suggestion**: add an FR-028 covering keyboard navigation, focus management on open/close, ARIA roles for the diff dialog, screen-reader announcement of "field changed" state, and a baseline that meets WCAG 2.1 AA contrast on the amber/blue treatments.

### 3e · Success Measurement

**P-004 (Recommendation)** — Success criteria are presence/absence-heavy. To know whether the feature actually replaces SDK usage post-launch, we need an adoption metric (e.g., the ratio of `update_deployment` mutations originating from the UI vs the SDK across a rolling window). The spec already has the rest in good shape.

**P-005 (Recommendation)** — No rollback trigger defined. Suggested: "if mutation error rate exceeds X% over Y minutes, the team disables the Edit configuration button via a feature flag while diagnosing." A single feature flag is cheap insurance.

## Engineering Lens Findings

### 4a · Architecture Soundness

**E-001 (Recommendation)** — Single TanStack Form instance for the whole drawer with ~200 fields is plausible but unproven for this codebase. The default behaviour of TanStack Form re-renders subscribed components on any field change unless `useStore(selector)` is used to scope updates.
**Suggestion**: commit to `useStore` selectors from day 1 in `<ChangedFieldFrame>` and section components; add a prototype stress test in slice 2 (drawer skeleton with a fake 200-field section) to catch perf regressions early.

### 4b · Failure Mode Analysis

**E-002 (🎯 Must-Address)** — Concurrent-edit detection is unaddressed. The spec's Edge Cases section mentions "another operator or SDK client mutates the deployment while the drawer is open" but neither plan nor research describes how the apply flow detects this or what the operator sees. Today the backend likely raises a generic `CONFLICT` (or stale-state) error; we should not surface that as a raw GraphQL error.
**Suggestion**: add FR-029 specifying that on apply, the client compares the `updatedAt` (or equivalent versioning field) on the deployment fetched at drawer-open to the deployment's current state pre-mutation, OR relies on a backend-provided optimistic-concurrency error code. On conflict, the dialog shows "this deployment was modified by Y at Z — reload to merge?", with a Reload action that refetches and shows the new diff baseline. Research note R-012 to document the chosen approach during slice 4.

**E-003 (Recommendation)** — Mutation timeout and network failure are not covered. FR-025 says the dialog stays open on failure; it should also distinguish a 5xx / network error from a validation error and surface them differently (transient vs sticky).

### 4c · Security & Privacy Review

**E-004 (🎯 Must-Address)** — Permission gating for the Edit configuration button. The drawer mutates server state; if the user doesn't have edit permission they should not be able to open the drawer. This is also a P-001 product gap.
**Suggestion**: add FR-030 — the Edit configuration button is gated on the same authorization check that `updateDeployment` enforces server-side. If the user lacks permission, the button is hidden (not disabled with a misleading tooltip) and the drawer route is not opened.

**E-005 (🎯 Must-Address)** — Env-var plaintext exposure deserves an explicit decision. The GraphQL `EnvVar.value` field's docstring says values are **not for secret material** — but operators may still have populated env vars with sensitive-looking strings. The spec should record the deliberate decision that the unified drawer continues today's posture (env values are visible to anyone with deployment read access) and that secret material belongs in a separate facility outside this feature's scope.
**Suggestion**: add an explicit assumption + ADR-style note in `research.md`.

### 4d · Performance & Scalability

**E-006 (Recommendation)** — The plan's "diff ≤5ms" claim is plausible but unverified. Add a small benchmark (vitest with `performance.now()` ranges) for the diff function under a worst-case shape (50 components × 50 fields each).

### 4e · Testing Strategy

**E-007 (🎯 Must-Address)** — The plan calls for unit tests on `lib/config-diff.ts` and `lib/config-impact.ts` but does not enumerate **tests per impact rule**. The rule matcher (`tolerations[*].effect value:NoExecute`) is bespoke glob syntax that is easy to get wrong, and a rule that fails to fire on a disruptive change directly undermines operator trust.
**Suggestion**: add to plan §Testing — "every entry in `impact-rules.ts` ships with at least one positive case (rule fires on the matching diff) and one negative case (rule does not fire on a similar but non-matching diff). The matcher's glob engine has its own dedicated unit suite covering each syntax form (`*`, `**`, `[*]`, `value:`, `kind:`)."

**E-008 (Recommendation)** — Component tests via Vitest + RTL are implicit but not stated. Recommended: at minimum, RTL coverage for the dirty-tracking behaviour of `<ChangedFieldFrame>` (the visual treatment is shared infrastructure across every section).

### 4f · Operational Readiness

**E-009 (Recommendation)** — No client-side analytics event planned for Apply & redeploy. Pairs with P-004 (adoption metric).

### 4g · Dependencies & Integration Risks

No findings. No new top-level deps; existing patterns reused.

## Resolutions Applied

Per `/speckit-auto-prep` autonomy rules, must-address items were patched directly into `spec.md` and `plan.md` rather than gated on user approval. Specifically:

1. **P-003 (Accessibility)** → `spec.md` FR-028 added covering keyboard nav, focus management, ARIA, and WCAG 2.1 AA contrast on the amber/blue treatments. Edge Cases section adds "screen reader users".
2. **E-002 / C-002 (Concurrent edits)** → `spec.md` FR-029 added describing detection + reload UX. `research.md` R-012 added describing the implementation choice (server-provided concurrency error code preferred; client-side `updatedAt` comparison as fallback).
3. **E-004 / C-001 (Permission gating)** → `spec.md` FR-030 added; Edit button is hidden when the user lacks edit permission. `spec.md` Assumptions revised to remove the "viewers can also edit" assumption.
4. **E-005 (Env var plaintext)** → `research.md` R-013 added; `spec.md` Assumptions documents the deliberate continuation of today's posture.
5. **E-007 (Per-rule impact tests)** → `plan.md` Testing section addendum: every rule in `impact-rules.ts` ships with a positive and negative test case; the matcher's glob engine has its own dedicated unit suite.

Recommendations (P-001 partial, P-002, P-004, P-005, E-001, E-003, E-006, E-008, E-009) are documented in this critique for the implementer to apply during the relevant slice. They do not block tasks generation.

Questions: none requiring stakeholder input — Q1 (TanStack Form perf) is resolved by E-001's mitigation, Q2 (support-ticket evidence) is not blocking, Q3 (cache staleness) is folded into the concurrent-edit fix.
