# Dual-Lens Critique: Anonymous opt-out telemetry for `styrminctl`

**Feature**: `015-styrminctl-telemetry` | **Date**: 2026-06-21
**Artifacts reviewed**: `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, constitution.

## Executive Summary

This is a strong, unusually well-specified feature. The privacy model is allowlist-by-construction
(a closed key set, names-not-values), the opt-out ladder is complete, and the latency/failure-isolation
guarantees are concrete and testable. The plan grounds every requirement in real prior art
(`TokenStore`) and a verified Cyclopts API (`parse_commands`, `parse_args` on 4.10.1).

The review surfaced **one must-address item** (E2E placement/harness ambiguity), four recommendations
(all narrow engineering hardening or doc-clarity points), and two questions. None are fundamental;
the feature is sound. **Verdict: ⚠️ PROCEED WITH UPDATES** — the must-address fix and the low-risk
recommendations were applied autonomously per the prep workflow.

## Product Lens Findings

### 3a. Problem Validation
Clear, evidenced ("decide blind"), appropriately scoped. The out-of-scope list (no spool/retry/batch,
no consent prompt, server side excluded) is crisp. No issue.

### 3b / 3c. User Value & Alternatives
The MVP decomposition (P1 dispatch, P2 opt-out, P3 CI-exclusion as independently shippable) is exactly
right. Reusing `TokenStore` and `httpx` over a third-party analytics SDK is the correct
build-vs-buy call for an anonymous, scrub-by-construction payload.

### 3d. Edge Cases & UX — **P1 (💡)**
The product chose **default-on with zero notice** (US5 "completely silent"; no first-run prompt). This
is an accepted industry pattern (Homebrew, .NET, Next.js) *but those tools print a one-time notice*.
There is a real tension between US5 (silent) and the trust story (US6/US9). See P1 in the table — the
spec now records the deliberate "silent + docs-only disclosure" rationale rather than changing
behaviour.

### 3e. Success Measurement — **Q1 (🤔)**
`event_id` is **deterministic** per `(install_id[:8], command)` (FR-012), and the server de-dups
(maintainer story 10). Consequently repeated invocations of the same command by the same install
collapse — you measure *per-install reach*, not *call frequency*. The PRD explicitly accepts dropped
repeat-counts, so this is intentional, but US1 ("which commands operators actually use") reads as if it
implies counts. Clarified in the spec.

## Engineering Lens Findings

### 4a. Architecture Soundness
Single chokepoint at `_AuthBoundaryApp.__call__`, one pure module per FR, command modules untouched.
Highly testable, no coupling. Good.

### 4b. Failure Mode Analysis — **E2 (💡)**
The daemon-thread + bounded-join dispatch is the right pattern for the hard latency cap. **Risk**: if
the interpreter exits while the dispatch thread is mid-flight (hung endpoint), CPython can print
`Exception ignored in thread ...` to **stderr** at shutdown — which would violate the byte-identical
stderr guarantee (FR-004 / SC-003). The thread target must have a top-level catch-all that swallows
everything (including during interpreter teardown), and a test must assert zero stderr noise when the
process exits with an in-flight/hung dispatch thread.

### 4c. Security & Privacy Review — **E1 (💡)**
Scrubbing is allowlist-by-construction — excellent. **Risk**: extracting option *names* must not
trigger Cyclopts value **conversion**. Resolving full `BoundArguments` for `--config @secrets.json`
could make Cyclopts read `secrets.json` (the `@file` convention) — wasteful, potentially failing, and
contrary to the "never touch values" guarantee. Research R3 already prescribes token-scan +
parameter-metadata lookup (no conversion); this must be stated as a hard constraint and covered by a
test that passes a `@file`/secret-bearing option and asserts the file is never opened.

### 4d. Performance & Scalability — **E3 (💡)**
The ≤200 ms budget is a wall-clock p99. A unit test that sleeps against a hung endpoint and asserts
`< 200 ms` is **flaky on loaded CI**. Prefer asserting the *mechanism* (injectable budget / mocked
join) plus a generous wall-clock guard (e.g. < 1 s) so the test proves "bounded" without depending on
scheduler timing. Common-case note: on a healthy endpoint the join still adds ~1 RTT (new TLS
handshake every invocation, no connection reuse) to interactive exit — within budget and acceptable for
coarse signal, but worth a comment so it isn't mistaken for a regression.

### 4e. Testing Strategy — **X1 (🎯, cross-lens)**
The plan places the E2E in `backend/tests/e2e/ (or cli E2E home)` — **ambiguous**. That suite is a
vCluster-on-Docker harness for Kubernetes flows; a CLI→local-HTTP-sink test needs **no cluster** and
would waste ~20 min + a vcluster per run if forced into it (and it's unclear which shard marker it
would carry). Constitution §V mandates an E2E "against real infrastructure, not mocks" — satisfied here
by the **real CLI process + a real local HTTP sink** (no mocks), which does not require a cluster. This
must be resolved before tasks so the implement phase doesn't either (a) bolt the test onto the vcluster
fixture or (b) skip it. **Resolution applied**: the E2E is defined as a real-subprocess, real-socket
test that explicitly does NOT depend on the `vcluster` fixture; placement + the no-cluster requirement
are now stated in spec.md and plan.md.

### 4f. Operational Readiness
No remote kill switch (server-controlled, out of scope) — acceptable. Opt-out levers are the
client-side "rollback". Fine.

### 4g. Dependencies & Integration — **Q2 (🤔)**
`httpx` promoted to a direct `cli` dependency. It is already transitive via `styrmin-sdk`, so the
lockfile is unchanged; this is plausibly outside the "Ask First: new dependencies" gate. Confirm with
maintainers (low-risk).

## Cross-Lens Insights

- **X1** (Testing × Scope): resolving E2E placement removes both a DoD ambiguity (product/§V) and a
  CI-cost/harness risk (engineering). Highest priority; applied.
- **E1** (Privacy × Correctness): the no-conversion constraint protects the privacy guarantee *and*
  prevents a functional defect (reading `@file` options). Both lenses converge.
