# Dual-Lens Critique: Backend No-Op Detection for Deployment Updates

**Date**: 2026-05-27 · **Inputs**: spec.md, plan.md, research.md, data-model.md, contracts/graphql.md
**Verdict**: ✅ **PROCEED** (must-address items folded into spec/plan; no RETHINK)

## 🎯 Must-Address

### M1 — Resolver must return `null` on a `None` service result (currently crashes)
Both resolvers end with `return Task.from_instance(task)` (`api/schema/mutation.py:805` and `:1115`). After the service returns `None` on a no-op, `Task.from_instance(None)` will fail. The resolver *signatures* are already `Task | None`, but the bodies are not None-safe.
**Fix**: guard both — `return Task.from_instance(task) if task is not None else None`. Captured as an explicit task. *(Engineering)*

### M2 — Scope "no side effects" precisely; `update_deployment` phase 1 still commits
`update_deployment` runs in two phases: phase 1 validates + writes the intent (`deployment.config = …`, name, merged parameters) and **commits unconditionally**; phase 2 generates the candidate instance and is where the new diff runs. So a no-op still incurs a phase-1 `save` + `commit`, bumping `deployment.updated_on` (and re-persisting identical config). SC-001's "no side effects" must not be read as "zero DB writes."
**Fix**: FR-001 + SC-001 reworded to scope the no-op guarantee to **no new `Instance`, no reconcile `Task`, `status` untouched, active-instance pointer untouched** — and an explicit note that `updated_on` may bump. Moving the diff ahead of phase 1 was considered and rejected (it would require generating the candidate from un-persisted state — a larger refactor that buys only an `updated_on` no-bump). Caller audit done: **only the two resolvers** call these functions; no internal callers (`redeploy_for_environment_update` uses `apply_state` directly), so the `Task | None` return change is contained. *(Engineering)*

## 💡 Recommendations

### R1 — Document the "rebuilt image under the same version" limitation
`apply` compares *resolved intent*. An application image rebuilt and re-pushed under the **same** app version, with unchanged config, resolves to an identical instance → no-op (no redeploy). This is correct for the version model but can surprise operators. Note it as a limitation; recovery is the future refresh path (D5). *(Product)* — applied to spec Assumptions/Out-of-Scope.

### R2 — Keep the flow-side Comparator as belt-and-suspenders
The Prefect `apply_state` flow re-diffs after dispatch. Post-change it will always find a diff (we only dispatch on a non-empty diff), so it is redundant but harmless. Do not remove it in this feature. *(Engineering)* — already in plan Risks.

## 🤔 Questions (resolved with judgment)

- **Should the phase-1 commit be skipped on a no-op?** No. The instance-level diff is the authoritative no-op signal and runs in phase 2; adding a phase-1 short-circuit would re-introduce a shallow change-detection check (the thing we are removing from the CLI) at the service layer. Accept the `updated_on` bump and document it (M2).
- **Does `unchanged` need a GraphQL enum/report now?** No — task-nullability carries the signal (research R8); a richer report is out of scope.
