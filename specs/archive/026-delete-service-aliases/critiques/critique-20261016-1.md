## Executive Summary

The spec follows the design brief closely and the plan keeps the fix in the two places that own aliases today. Two items must change before tasks. First, a restore deletes the target namespace, which deletes the StyrminDeployment in it and makes kopf run the delete handler's teardown. With the planned alias step, that teardown would delete the aliases of a deployment that keeps running, and Velero does not restore them, because they are in other namespaces. Second, FR-007 and FR-008 require that a flow writes nothing after the request, which no read-then-write can guarantee; the plan's research already says so, but the requirements still state the stronger rule. The other findings are smaller: a user-visible effect of the fix that the spec does not state, concurrency of the new reads, and test coverage of the new guard.

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | A same-target or cross-target restore deletes the target namespace (`execute_velero_restore` in [`workflows/templates/backup.py`](../../../backend/styrmin_backend/workflows/templates/backup.py)). The namespace deletion deletes the StyrminDeployment, and kopf runs `kopf_on_styrmin_deployment_delete`, which runs `_teardown_owned_resources` ([`operator.md`](../../../dev/knowledge/agent/operator.md), "Deletion", which describes this for restores). With the planned first step, a restore would delete the restored deployment's aliases in every other namespace. Velero restores only the target namespace, and the restore flows write no alias (no code outside `service_aliases.py` and `orchestration.py` calls the alias functions), so the other deployments' pods could not resolve the restored deployment's short names until the next create, update or upgrade. | Delete aliases only when the deletion is a deletion of the deployment: when `spec.deletionRequested` is true, or when the StyrminDeployment is deleted while its namespace is not being deleted (`kubectl delete styrmindeployment`). When `spec.deletionRequested` is false and the namespace is `Terminating` or gone, the step deletes no alias and logs why. If reading the namespace fails, the step deletes no alias, because deleting the aliases of a running deployment is worse than leaving aliases that the next flow overwrites. Add a requirement, an edge case, research R-011, and unit tests. |
| E2 | 🎯 | FR-007 and FR-008 say that no flow writes after the request, including a flow whose context was built before it. A flow reads the cluster and then writes, so a write can follow the request by milliseconds; research R-004 says so, and the spec's planning clarification records it. As written, the requirements cannot be met or tested. | Reword FR-007 as the outcome: a flow writes no alias of a deployment whose deletion it can read, and deletes any alias of that deployment it wrote before it could read the request, so that no alias remains. Reword FR-008: a flow writes nothing into the namespace of a deployment whose deletion it can read, and never creates another deployment's namespace. |
