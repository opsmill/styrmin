# Critique: Driver-Side Env Var Consumption (010)

**Date**: 2026-05-08
**Spec**: [`spec.md`](../spec.md)
**Plan**: [`plan.md`](../plan.md)
**Reviewers**: Product Lens (CEO/PM mindset) · Engineering Lens (Staff Engineer mindset)

## Executive Summary

This is a deliberate course-correction on a known-broken feature (008's post-render env-vars injection clobbers chart-default env entries). The spec is tight and well-scoped: it deletes the broken layer, exposes env vars where the chart-rendering layer can consume them, and preserves the operator-facing contract (configuration model, validators, query surface, mutation, frontend).

The dual-lens review surfaces **one must-address finding** (SC-002 lacks a dedicated test assertion) and **two recommendations** (yaml-escaping in driver guide, completeness of alternatives in research). All three have small, surgical fixes. No fundamental product or architecture concerns.

**Verdict**: ⚠️ **PROCEED WITH UPDATES** — fixes will be applied inline before tasks generation, per the auto-prep workflow.

## Product Lens Findings

### 3a. Problem Validation
The user surfaced the bug interactively after reading the 008 implementation report. The pivot is justified by concrete code (`EnvVarsPatch` doing JSON-patch `replace` on container[0]'s env list). No additional validation needed.

### 3b. User Value Assessment
The four user stories map cleanly: US1 + US2 are the load-bearing pair (template-context exposure + delete the broken injection); US3 demos via simple-app; US4 documents. MVP analysis: US1+US2+US3 are the genuine MVP; US4 is operator-friendly polish that ships in v1.

### 3c. Alternative Approaches
Research §2 considered phased deletion (rejected — no legitimate users) and §1 considered exposing a top-level `env_vars` rendering key (rejected — namespace consistency). **One alternative not enumerated** that reviewers will likely ask about: could we fix the injection layer to merge env entries instead of replacing? See **E3 (recommendation)**.

### 3d. Edge Cases & UX
Spec §"Edge Cases" covers the relevant scenarios. Driver-author migration story is explicit: existing drivers must add explicit env-var consumption to keep operator-set env vars working. The simple-app chart may need extension (FR-013 calls this out).

### 3e. Success Measurement
SC-001..SC-006 are measurable. **SC-002 ("chart-default entries unchanged") is the load-bearing scenario** — the difference between the broken 008 path and the corrected 010 path. But the existing 008 E2E test (which 010 retains) only asserts that operator-set entries reach the pod; it does NOT assert chart-default entries are preserved. The contract is technically satisfied as long as the chart's defaults survive — but without a dedicated assertion, a regression that re-introduces the clobbering would still pass the existing E2E. See **E1 (must-address)**.

## Engineering Lens Findings

### 4a. Architecture Soundness
The pivot strengthens layered architecture: removes code that incorrectly straddled agent and chart-rendering layers. Driver-side consumption is the same shape as every other config field consumption (scheduling, ip_whitelist, etc.). Minimal new code; mostly deletion.

### 4b. Failure Modes
- **🎯 E1 (must-address)**: SC-002 is not exercised. The existing 008 E2E asserts `LOG_LEVEL=debug` reaches the pod after the operator sets it — but the chart-default-preservation invariant (the entire reason for this feature) has no dedicated assertion. A regression that re-introduces clobbering would pass the existing E2E. **Fix**: extend the E2E with an explicit assertion that at least one chart-default env entry is present alongside the operator-set entries. The simple-app chart's existing `env:` defaults (or chart-default entries via the postgresql sidecar) are the natural assertion target.
- **💡 E2 (recommendation)**: yaml-injection in driver templates. A naive driver template emits `"{{ value }}"` without escaping; an operator submits a value containing `"\nlist:\n  - bad"`; the rendered values.yaml breaks. This is driver-author-land (the platform doesn't impose policy), but the new driver-author guide MUST cover value escaping (Jinja `tojson` filter or equivalent quoting). Currently the spec doesn't mention this. Add to FR-022 (the worked-examples requirement) and to research §3 (the simple-app demo).

### 4c. Security & Privacy
The yaml-injection point above is in driver-author hands. AGENTS.md threat model: operators are trusted to set env-var values; driver authors are trusted to render them safely. The platform's validation is name-regex + size-caps — appropriate. No new auth surface.

### 4d. Performance & Scalability
Deletion-only on the platform side. Net positive on reconcile latency (one fewer post-render patch per pod-template-bearing kind per deployment). No concerns.

### 4e. Testing Strategy
- The verification test for FR-001/FR-002 (`test_render_value_template_env_vars.py`) is well-scoped — synthetic `GlobalContext` + probe Jinja template + assert rendered output.
- The deletion sweep removes existing tests cleanly (deleted, not skipped — Constitution §V "no fake-passing tests" honoured).
- The retained E2E body is unchanged but the render path differs. Combined with E1's must-address, the testing story becomes: "operator sets env, pod has it AND chart defaults preserved" — both as one assertion suite.

### 4f. Operational Readiness
- Drivers that don't consume env vars silently no-op for env-var operators. Documented as opt-out behaviour. **Telemetry consideration**: ops could want a "operator set env vars but driver doesn't consume them" signal. Detecting this requires inspecting rendered values, which is heavy. Defer.

### 4g. Dependencies & Integration
- 008 PR (#197) coordination is a merge-time concern, captured in research §8 + spec §Assumptions. No spec change needed.
