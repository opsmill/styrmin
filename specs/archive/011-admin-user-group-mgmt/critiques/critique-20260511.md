## Executive Summary

The spec and plan are well-shaped: scope traces cleanly to issue #180's 33 user stories, the layered architecture obeys Constitution §III, propagation tests for every new GraphQL field are enumerated (§V), and the auth-lifecycle E2E is dual-entrypoint as required (§V). Two engineering issues warrant **must-address** edits before tasks: (1) the last-admin guard, as currently described, is not transaction-safe and can be defeated by two concurrent demotions, and (2) the GraphQL request-logging path will capture plain-text passwords for `createUser`/`resetUserPassword`/`changePassword` unless the field is masked. Three further recommendations cover N+1 risk on `users` query, weakening SC-007's measurability, and adding admin-audit logging.

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 🎯 | **Last-admin guard race**. Data-model.md says "Pre-condition is checked at request time against current state". With two concurrent transactions (Tx A demotes admin X, Tx B demotes admin Y), both can read the snapshot showing two admins, both pass the guard, both commit, and the system ends with zero admins — lockout. | **Make the guard transaction-safe.** Either (a) acquire row-level locks (`SELECT ... FOR UPDATE`) on every admin-conferring row (active admins + admin groups) at the start of the mutating transaction; or (b) run the guard query inside a `REPEATABLE READ` (or stricter) transaction and rely on the DB to abort one of the conflicting transactions. Document the chosen approach in research.md and add an integration test that simulates two concurrent demote requests and asserts at least one fails. |
| E4 | 💡 | `resetUserPassword` and `deactivate` invalidate sessions in the same transaction — good. But the *order* matters: if the password write fails after the session-delete succeeds, the user is logged out without a password change. Need to confirm the password update precedes the session deletes within the transaction so the rollback is a no-op on both. | In the service-layer function for both operations, write the password/active flag first, then delete sessions, then commit. Add a unit test that monkeypatches the password write to raise and asserts neither change persists. |

## Recommended Actions

### 🎯 Must-Address (Before Proceeding)

1. **E3 / X1 (Last-admin race)** — Apply inline to `spec.md` and `plan.md`:
   - In `spec.md`, extend FR-010 to require transactional guarantees ("checked under a serializable read or with row-level locks on admin-conferring rows in the same transaction as the mutation").
   - In `plan.md` Phase 0 (`research.md` D1), add the chosen concurrency strategy.
   - In `contracts/graphql.md`, add `test_concurrent_demote_last_admin_serialized` to the test matrix.

2. **E5 / X2 (Password masking)** — Apply inline:
   - Add FR-029 to `spec.md`: every GraphQL field whose name is in the password-name allow-list MUST be masked in request logs.
   - In `plan.md` (or `research.md` D-new), record the masking-middleware decision.

### 💡 Recommendations (Strongly Suggested, applied opportunistically)

1. **P5** — Add Edge Case: inline error on self-edit rejection.
2. **P7** — Relax SC-007 to a structural fixture-shape check.
3. **E4** — Tighten transaction order: write password/active flag first, then delete sessions.
4. **E9** — Use `selectinload(User.groups)` in the `users` resolver.
5. **E10** — Add concurrent-demote integration test alongside E3 fix.
6. **E12** — Add FR-030 for admin-mutation audit log line.
