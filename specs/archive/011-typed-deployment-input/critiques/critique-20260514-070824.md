# Critique Report: Typed `UpdateDeploymentInput` GraphQL Surface

**Date**: 2026-05-14
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES → ✅ APPLIED (must-address fixes + low-risk recommendations applied inline; see "Resolution" section at end)

---

## Executive Summary

The spec is a clean, well-scoped port of the 009-environment-update pattern with the right behaviour-bearing decisions made explicit (parameters-merge asymmetry, two new typed errors, hard cutover). The plan correctly identifies every in-tree consumer and locks the major implementation choices in `research.md` with rationale and rejected alternatives. Constitution gates all pass.

Two real defects in the plan need to be fixed before tasks generation: (E1) the proposed `ServiceNameOverride → ServiceNameOverrideInput` rename would silently change the schema of the out-of-scope `Deploy` mutation, because that type is *shared* between the two mutations — an unintended ripple beyond the feature scope; (E2) `ParameterValueInput.value: JSON!` has no documented size constraint, opening a small DoS surface that the spec is silent on. Both are mechanical to address inline.

Several recommendations would meaningfully strengthen the design without blocking: (E3) the 33-test propagation matrix should be parametrised to keep the test code maintainable; (E4) the new `deploymentConfigToInput` frontend helper needs dedicated Vitest coverage, not just caller-level coverage; (E5) the coordinated rollback story (backend revert requires SDK + frontend regen revert) should be documented in the plan; (P1) SC-001's "no source-reading required" claim is only meaningful if every input field carries a description, which neither the spec nor the contracts currently mandate.

Verdict: ⚠️ PROCEED WITH UPDATES — apply E1 + E2 + the description-requirement piece of P1 inline, accept E3/E4/E5 as recommendations to surface in tasks, then proceed to `/speckit-tasks`.

## Resolution (applied 2026-05-14, same session)

### E1 — APPLIED 🎯

### E2 — DOWNGRADED to clarification 💡 → APPLIED

Closer reading of `backend/styrmin_backend/services/parameters.py:14-19` shows the existing `validate_parameter_values` constrains parameter values to scalar kinds (`STRING`, `INTEGER`, `BOOLEAN`, enum-as-string) via `_KIND_TYPES`, with type-mismatch rejection. The DoS surface is therefore narrower than originally framed: only string values are unbounded, which is **already** today's behaviour. Adding a byte-size cap would be a behavioural change that exceeds the spec's "pure GraphQL-surface change" promise. Instead of adding a new FR, added an explicit Assumption to `spec.md` documenting that today's parameter-value validation is preserved unchanged and that adding a byte-size cap is out of scope. This satisfies the underlying concern ("the spec should declare the contract") without scope creep.

### E8 — APPLIED 💡
