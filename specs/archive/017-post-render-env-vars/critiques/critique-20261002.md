## Executive Summary

The problem is concrete and reproduced (#334 crash-loop, #385 root cause), the mechanism was
verified against real kustomize before design, and planning surfaced two facts the brief missed:
patched entries and the patched container move first, and merge-patch leaves pre-migration
values-template env behind (FR-011). Two must-address gaps remain, both in the FR-003 write
validator (D-007): as written it would reject the removals FR-006 promises, and it validates
against the pre-switch driver version, which lets a version-switching write store values that are
never applied, breaking SC-005. Both are local fixes. The recommendations tighten test coverage
(E2E for `valueFrom` replacement, YAML scalar coercion), the migration story (Jobs and
initContainers no longer receive user env vars; old-version deployments fail on the next
environment fan-out), and the driver-author surface (component container on the driver detail
tab). Verified during review: the StyrminDeployment CRD preserves unknown context fields, so the
new `container` field survives the instance-context round-trip; Ready deployments are not
re-rendered by the operator's resume or drift timer, so FR-007 failures appear only on the next
spec change.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | D-007's rule "reject when the submitted block differs from the stored one" also rejects **removals**: dropping one key from a containerless component's stored block differs from the stored block, so the FR-006 "remove" control would fail with `COMPONENT_CONTAINER_NOT_DECLARED`. | Reject only when the submitted block **adds a key or changes a value** relative to the stored block; unchanged re-submissions and removals (submitted ⊆ stored) pass. Update research D-007, data-model §5, contracts/errors.md, spec FR-003. |
| E2 | 🎯 | D-007 validates against the deployment's **current** driver version (mirroring `_validate_component_env_var_targets`). When one `updateDeployment` call (or a `styrminctl apply` manifest) both switches driver version and writes component env vars, a component that loses its container in the target version accepts new values that are never applied — a silent no-op SC-005 forbids. The reverse case (target adds a container) is wrongly rejected. | Run the container validator against the driver version the deployment will be pinned to after the mutation (resolved before any task is submitted). Leave the existing unknown-component check unchanged. |
| E3 | 💡 | D-003's single JSON Patch uses per-key `add /metadata/labels/<key>` ops, which fail if a map is absent, and the kopf operator writes its own annotations on HelmReleases it handles (`handlers/helmrelease.py`). | Unit-test that kopf annotations and Flux's finalizer survive an update, and that the patch is built with a whole-map `add` only when the live map is absent (or always ensure the builder sets both maps, which it does today — pin that with a test). |

### Security & Privacy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E5 | 💡 | User values are embedded as YAML inside a Kustomize patch string. Scalars such as `"true"`, `"null"`, `"0123"`, `""`, multi-line strings, or `$(VAR)` must stay strings through `yaml.dump` → Flux's YAML parse. A coercion bug would turn `"null"` into an absent value or `"true"` into a boolean the API rejects. | Unit-test `ContainerEnvPatch.render_value()` round-trips those values as strings (`yaml.safe_load` of the rendered patch). Names are already POSIX-validated and container names DNS-1123-validated, which closes structural injection. |
