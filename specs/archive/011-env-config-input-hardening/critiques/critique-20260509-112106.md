## Engineering Lens Findings

### 4a. Architecture Soundness
Reuses existing patterns at every layer. The schema-walking propagation test (US1) is a cleaner pattern than per-field assertions for completeness checks; worth adopting more broadly in future features.

### 4b. Failure Modes
- **🎯 E1 (must-address)**: research §2 + data-model §4.3 say the `api_driver`'s `update_environment_via_form` "Reads the existing config, constructs an UpdateEnvironmentInput, submits via the SDK". This is the SAME read-then-build-input-then-submit flow the frontend's `buildFullReplacementInput` does. If the api_driver reads raw JSON config and builds the input WITHOUT the value-transform layer, it has the SAME enum-corruption bug US2 is fixing in the frontend — defeating dual-entrypoint coverage. Either pin "the api_driver builds via `EnvironmentConfig.model_validate(config)` so Pydantic handles coercion automatically (no manual transform needed)" OR pin "the api_driver applies the same transform". Spec is silent.
- **💡 E2 (recommendation)**: T061's test body becomes the parity test — it runs under both `[api-chromium]` and `[ui-chromium]` and asserts the same observable outcome. Worth surfacing in spec/research that this parametrisation IS the parity check (no separate parity test needed); makes the design intent explicit.

### 4c. Security & Privacy
No new auth/security surface.

### 4d. Performance & Scalability
Marker cleanup doubles E2E time for affected tests; accepted per AGENTS.md.

### 4e. Testing Strategy
Comprehensive. The schema-walking test (FR-002) is the structural guarantee; per-field tests for the new fields cover the value-level round-trip; Vitest covers the frontend transform; T061 covers the form flow.

### 4f. Operational Readiness
No production-path changes. Validator hardening (US3) improves observability — typed error code instead of 500.

### 4g. Dependencies & Integration
No new dependencies. The 008→009→010→011 stack accumulation is the only coordination concern; covered in spec §"Branching" + plan §"Structure Decision".

## Cross-Lens Insights

- **🎯 X1 ≡ E1 (must-address)**: api_driver / ui_driver parity for `update_environment_via_form`. Both lenses agree this is load-bearing for the dual-entrypoint promise.
- **💡 X2 ≡ E2 (recommendation)**: dual-entrypoint coverage IS the parity test — but only if the api_driver reads via the typed config path (not raw JSON). Tightening the spec on this makes the test design transparent.
- **🤔 Q1 (resolved)**: should we also add an inverse-direction completeness check ("input fields without Pydantic counterparts")? **Resolved: no.** That's a different bug class (zombie input fields), out of scope for this hardening pass. If the input later gains a field that doesn't map to Pydantic, the SDK will still surface it but the backend `EnvironmentConfig.model_validate` will silently drop it — visible at the next propagation test or by a curious operator. Not load-bearing; future feature if it ever happens.
