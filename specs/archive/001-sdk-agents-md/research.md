# Research: Python SDK AGENTS.md

**Feature**: 001-sdk-agents-md
**Date**: 2026-05-01

This feature is documentation-only; "research" here means surveying existing
repo conventions and the SDK source so the new doc accurately reflects them
and stays consistent with sibling docs.

## R1 — Tone and structure of sibling AGENTS.md files

**Decision**: Follow the structure already established by `backend/AGENTS.md`
and `frontend/AGENTS.md`. Sections, in order:

1. One-line description of the area.
2. **Tech Stack** (bullets, key technologies only).
3. **File Structure** (tree or table covering the package's top-level layout).
4. **Commands** (commands relevant to this area, fenced bash blocks).
5. **GraphQL Workflow** (SDK-specific — see R2).
6. **Coding rules** (concise bulleted rules; cross-references to dev/ where relevant).
7. **Always Do / Ask First / Never Do** (mirroring root `AGENTS.md`).

**Rationale**: Consistency across `AGENTS.md` files reduces cognitive load for
agents that read multiple at once. The structure already proven for the two
peer docs is sufficient.

**Alternatives considered**:

- Free-form prose: rejected — agents benefit from predictable section
  anchors (e.g., "boundaries").
- Replicating root `AGENTS.md` headings verbatim: rejected — too long; the
  per-area docs are deliberately tighter than the root doc.

## R2 — Where to draw the line with the root `AGENTS.md`

**Decision**: The SDK doc references repo-wide GraphQL conventions in the
root rather than restating them. Specifically: it links to or names the root
`AGENTS.md` "GraphQL Queries" and "GraphQL Schema" sections for rules that
apply to **all** `.graphql` files in the repo (one operation per file,
snake_case naming, named operations only, regen commands, validate-graphql
step). The SDK doc's own GraphQL section focuses on what is **SDK-specific**:
the `load_query()` import path, the `_generated/` directory's role, and the
manual-Python-wiring step that is the central pitfall called out in #150.

**Rationale**: Duplication across `AGENTS.md` files is the most likely cause
of doc rot; if a regen command changes, only one file should need updating.
The root doc is loaded into agent context via `@AGENTS.md` from `CLAUDE.md`,
so referencing it costs nothing.

**Alternatives considered**:

- Restate everything in the SDK doc for self-containment: rejected — drift
  risk, and the audience already has the root in context.

## R3 — Source of truth for SDK module roles

**Decision**: Describe each top-level module under
`python_sdk/src/styrmin_sdk/` by reading the current source. Roles to capture:

| Module / dir | Role |
|---|---|
| `client.py` | `StyrminClient` — public entry point. Constructs the transport and instantiates one resource object per area (clusters, environments, deployments, drivers, tasks, backups, schedules, backup-storage-locations). Exposes them as attributes on the client. |
| `_transport.py` | `Transport` — internal HTTP + GraphQL execution layer over `httpx.AsyncClient`. Handles `/graphql` POSTs and raw GETs. Wraps HTTP errors into `StyrminTransportError`. |
| `_queries.py` | Single `load_query(name)` helper that reads `graphql/<name>.graphql` and returns the query string. |
| `exceptions.py` | `StyrminError` and subclasses (`StyrminTransportError`, `OperationFailedError`, `ResourceAlreadyExistsError`, `ResourceNotFoundError`). |
| `resources/` | One `*Resource` class per area. Each inherits from `_base.BaseResource` and exposes async methods that load a `.graphql` file, send it through the transport, check structured GraphQL errors, and return generated Pydantic types. |
| `resources/_base.py` | `BaseResource` (held transport ref + helpers): `_parse()` validates an outer generated model and extracts the inner field; `_check_graphql_errors()` raises typed exceptions based on `extensions.code`. |
| `graphql/*.graphql` | One operation per file; file name is snake_case of the GraphQL operation name. |
| `graphql/_generated/` | Pydantic models regenerated by `uv run invoke generate`. Never edited by hand. |

**Rationale**: These are the modules an agent will actually touch. Mentioning
each in the doc gives the reader an entry point.

## R4 — The "regen is not enough" warning

**Decision**: The doc must contain an explicit, prominent warning — not a
footnote — that goes roughly:

> Adding a `.graphql` file and running `uv run invoke generate` does **not**
> expose the new operation through the SDK. The client (`client.py`) and the
> matching resource module (`resources/<area>.py`) must also be updated by
> hand. If the operation belongs to a new area with no existing resource,
> a new resource module must be created and instantiated in
> `StyrminClient.__init__`.

**Rationale**: This is the single failure mode #150 calls out by name.

**Alternatives considered**:

- Embed the warning inside a long workflow section: rejected — easier to
  miss. A standalone callout makes it unmissable.

## R5 — Worked example

**Decision**: Include a short snippet derived from `ClusterResource.get`
(already in `python_sdk/src/styrmin_sdk/resources/clusters.py`) showing
`load_query()`, `_transport.execute()`, `_check_graphql_errors()`, and
`_parse()` in concert. Keep the example to ~10 lines.

**Rationale**: A reader who can see one method end-to-end can pattern-match
their new operation onto it without further reading.

**Alternatives considered**:

- Synthetic example: rejected — drift risk vs. real code; using a real
  method anchors the example to maintained source.

   Add a "Python SDK" entry between Frontend and Drivers.

**Rationale**: Minimal, low-risk, mirrors the issue's acceptance criteria
exactly.

## R7 — Constitution §V (E2E test) handling

**Decision**: Document the E2E exemption explicitly in `spec.md`'s
Assumptions section (already done) and in `plan.md`'s Constitution Check
table. Reviewer approval of the spec/plan acts as the explicit confirmation
required by §V for skipping E2E coverage on a docs-only change.

**Rationale**: §V requires the reviewer's approval, not the implementer's
own judgment, to skip E2E. Surfacing the exemption in plan + spec puts the
decision visibly in the reviewer's path.
