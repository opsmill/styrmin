# Critique: Environment-Config Update with Deployment Fanout (009)

**Date**: 2026-05-07
**Spec**: [`spec.md`](../spec.md)
**Plan**: [`plan.md`](../plan.md)
**Reviewers**: Product Lens (CEO/PM mindset) · Engineering Lens (Staff Engineer mindset)

## Executive Summary

The spec is well-grounded — it directly addresses a correctness gap surfaced by the post-008 review (env vars set at the environment scope didn't propagate to existing deployments without a manual reconcile). The plan reuses load-bearing infrastructure cleanly: the typed input mirrors the post-008 Pydantic shape, the fanout reuses `update_deployment_version`'s instance-generation pipeline, and the frontend extends the existing tabs scaffold. None of the design choices are architecturally questionable.

The dual-lens review surfaces **two must-address findings** and **four recommendations**. Both must-addresses concern the interaction between the no-op detection (FR-010) and the per-deployment fanout — specifically a partial-fanout-recovery footgun that the current spec doesn't cover and a UoW-commit-ordering invariant that's load-bearing but not explicitly stated. Both have small, surgical fixes.

**Verdict**: ⚠️ **PROCEED WITH UPDATES** — fixes will be applied inline before tasks generation, per the auto-prep workflow.

## Product Lens Findings

### 3a. Problem Validation
The post-008 auto-implement report explicitly flagged the propagation gap. The user surfaced it again in conversation. The four user stories map cleanly to the four requirements the user enumerated. No concerns.

### 3b. User Value Assessment
- **MVP analysis**: US1+US2 (backend correctness + structured input) is the load-bearing pair. US3+US4 (frontend) are operator-UX wrappers that the API layer doesn't need to ship.
- **SDK UX concern (P1 below)**: full-replacement semantics force SDK consumers into read-modify-write — error-prone. The frontend form mediates this for the env-vars-only case, but SDK users don't get that mediation.

### 3c. Alternative Approaches
The user explicitly considered and rejected: partial-update with `UNSET` sentinels, reconcile-only (instead of full redeploy), and event-driven config propagation. The chosen approach is the simplest path that satisfies the user's stated requirements; no overlooked alternatives.

### 3d. Edge Cases & UX
Spec covers many edge cases. Two gaps worth flagging:
- **100%-failure scenario** (Q1 below): when a new config makes every deployment fail to render, the env-config row persists anyway and the operator sees universal failure. This is per FR-008 by design — confirming intentional.
- **Partial-fanout-then-retry** (X1 below): the no-op detection silently skips the retry path for laggards.

### 3e. Success Measurement
SC-001..SC-010 are measurable. **Missing fanout-failure-rate metric** (P2) — useful operational signal not currently tracked.

## Engineering Lens Findings

### 4a. Architecture Soundness
Reuses the existing `update_deployment_version` pipeline by extracting a `redeploy_for_environment_update` helper. Clean. One layering note: the helper lives in `services/deployment.py` and is called from `services/environments.py`, creating an `environments → deployment` import direction that doesn't exist today. Not circular (deployment doesn't import environments), but worth verifying at implementation time.

### 4b. Failure Modes
- **🎯 X1 (must-address)**: partial-fanout-recovery footgun. If the fanout dispatches Tasks for deployments 1..24 successfully and then hits a transient Prefect dispatch error on deployment 25, the loop logs the failure and continues. The operator sees a partial fanout. They retry by submitting the same input — but per FR-010, that's a no-op (canonical equality holds), so the fanout is **skipped**. Deployments 25..N never reconcile to the new config. **Real correctness gap.** Fix below.
- **🎯 E1 (must-address)**: UoW commit ordering. The plan's pseudocode commits the env-config row before the fanout loop, which is correct — but the spec doesn't pin this as a requirement. If a future maintainer reorders the dispatch to happen inside the same UoW transaction, a UoW rollback could leave persisted Tasks for an env-config that was rolled back. Pin as an FR.
- **💡 E2 (recommendation)**: sequential fanout dispatch latency. For an environment with 100 deployments, dispatching Tasks sequentially via the Prefect API at ~50ms each adds ~5 seconds to mutation latency. Parallelise with `asyncio.gather` and a concurrency cap.

### 4c. Security & Privacy
No new auth surface. The fanout dispatches Tasks the platform already has authority to dispatch. No concerns.

### 4d. Performance & Scalability
See E2 above. No other concerns at the scales the platform targets today.

### 4e. Testing Strategy
- Mandatory E2E (US1 headline + failure-isolation) and propagation tests per new field/argument are scheduled. ✅
- The propagation matrix in `contracts/graphql.md §4` includes the no-op-skip behavioural row. ✅
- **Missing partial-fanout-recovery test** (E3): once X1's fix lands, the regression test for it must be added.

### 4f. Operational Readiness
- One structured log per fanout dispatch is planned. ✅
- **💡 E4 (recommendation)**: no metrics for fanout dispatch count or per-deployment failure rate within fanouts. Not blocking for v1; useful operational signal.

### 4g. Dependencies & Integration
No new dependencies. Integration with existing Prefect Task machinery and the post-008 validation pipeline. No risk flags.

## Cross-Lens Insights

- **🎯 X1 (must-address)**: full-replacement + sequential fanout dispatch + no-op detection together create a partial-fanout-recovery footgun. Addressed below.
- **💡 P1 (recommendation)**: full-replacement-via-SDK is genuinely awkward for "I want to add one env var" callers. The frontend form mediates this; SDK consumers don't get that mediation. Document the read-modify-write pattern explicitly in the spec assumptions or in research.md so SDK consumers know the contract.
