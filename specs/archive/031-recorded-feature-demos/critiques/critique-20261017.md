## Executive Summary

The spec follows the PRD closely, and the planning research resolved every dependency question from source code, release notes and one test image build. Research found two facts the PRD did not foresee: the `infrahub` driver cannot take an environment backup, and a clone probably keeps the source's service aliases. The spec and plan record both and flag them for the maintainer.

Two items block tasks:

- The plan names "wait for the update task" and "wait for the upgrade task" in demos 1 and 2, but no page object or driver method waits for a task to finish. The UI driver's `wait_for_deployment_running` can return before the task starts, so the speed-up would cover the wrong time and the next step could run on a deployment that is still changing.
- The plan offers landing the FR-016 check as `xfail(strict=True)` if it fails. Constitution §V requires a modified E2E test to be observed to PASS. The plan also does not say that demos 1 to 3 can go on while demo 4 waits for a product fix, or when the pull request can merge.

Both have clear fixes. The other findings are a gap in what the FR-016 check proves, memory left by kept environments, and network access the guide should name.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | Demos 1 and 2 wait for an upgrade task and for update tasks, but nothing in the plan waits for a task to finish. `UiScenarioDriver.set_component_image`, `set_component_replicas` and `upgrade_deployment` return when the change is submitted, and `wait_for_deployment_running` reads the header badge, which can still show `Running` before the task starts. The wait would then end at once: the speed-up would cover the wrong time, and the next step would start while the deployment is still changing. The demo scripts cannot add selectors (FR-003). | Add a page-object method to `DeploymentDetailPage`, for example `wait_for_new_task(task_type, *, known_task_ids, timeout)`, that reads the timeline's `data-task-id`, `data-task-type` and `data-task-result` attributes (already used by `read_timeline`) and waits until a task that was not there before reaches a terminal result, failing on a failed result. Expose it through the demo scripts' recorder wait. Add it to the plan's design and to the source tree. |
| E2 | 💡 | Page objects are also created outside `UiScenarioDriver`, for example `LoginPage` in tests and fixtures. The plan does not say that those keep `keystroke_delay_ms=None` and that a page object that creates another page object passes its setting on. | State in the plan that the setting is a keyword argument with default `None` on every page object, and that any page object or driver that creates another one passes it on. |
