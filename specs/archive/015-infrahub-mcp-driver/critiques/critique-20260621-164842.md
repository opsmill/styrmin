# Critique Report: Infrahub MCP Server Application Driver

**Feature**: 015-infrahub-mcp-driver
**Date**: 2026-06-21 16:48:42
**Artifacts reviewed**: `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, `.specify/memory/constitution.md`

## Executive Summary

This is a tightly-scoped, config-only example Driver backed by an unusually complete PRD. The spec and plan are internally consistent, reuse existing platform machinery (manifest schema, parameter model + validator, Component/Service/render), and introduce no new code paths. Security posture is strong by construction: token-passthrough means **no credential is ever stored or surfaced** (FR-006 / SC-004), and the Service is `internal` scope (least privilege).

**No 🎯 Must-Address items.** The single notable deviation — skipping the Constitution §V E2E requirement — is an explicitly owner-approved, documented exception (recorded in spec Assumptions/Out of Scope and plan Complexity Tracking), not an ungoverned violation. The residual risks are all already captured as the PRD's Open Question (chart coordinates + selector label) and are scheduled for implementation-time verification.

**Verdict: ✅ PROCEED** to `/speckit-tasks`.

## Product Lens Findings

### 3a. Problem Validation
- Clear, real pain point: operators today can only run the Infrahub MCP server via Docker Compose outside Styrmin, losing lifecycle/reconciliation/observability. Tied to issue #271 (and related #270/#263). No concern.

### 3b. User Value Assessment
- Every user story delivers value; US1 is a self-contained MVP (deploy in passthrough mode). US2/US3 are independent, additive safety/operability knobs. Acceptance criteria are outcome-oriented. No gap in the core journey.

### 3c. Alternative Approaches
- The simplest viable solution *is* what's proposed: a stripped-down single-Component Driver reusing existing machinery. No custom code, no new entity. Good restraint — the plan explicitly rejects copying `infrahub` wholesale (six Components, backups, actions).

### 3d. Edge Cases & UX
- Edge cases are enumerated and sensible (unreachable/omitted address, invalid log level, future MCP v2 excluded by `supported_versions`).
- **P1 (💡)**: `infrahub_address` is validated only as a *string*, not as a URL. A malformed value (e.g. `not a url`) passes validation and fails at agent-query time. This is consistent with the documented "failures surface at query time" edge case, so it is acceptable for v1 — but worth a one-line note in operator-facing docs.

### 3e. Success Measurement
- SC-001..004 are measurable and verifiable at the unit level. **P2 (💡)**: SC-002 is phrased in implementation terms (`values.j2.yml`, `fullnameOverride`, `mcp.authMode`). For a Driver-authoring feature these are the genuine user-facing surface (the requirements checklist already notes this), so the concreteness aids verification rather than leaking detail. No change required.

## Engineering Lens Findings

### 4a. Architecture Soundness
- Driver-layer-only change; reuses `DriverSpec`, `DriverParameterDefinition`, `validate_parameter_values`, and the render path unchanged. Testable at the unit layer. No coupling introduced. Sound.

### 4b. Failure Mode Analysis
- Passthrough design means the server starts regardless of Infrahub reachability; failures are deferred to query time with the client's token. Documented and accepted for v1. No blast radius beyond the single Deployment.

### 4c. Security & Privacy
- Strongest aspect of the design: no stored token (FR-006), `internal` Service scope, optional `mcp_read_only` for less-trusted agents. Access remains gated by Infrahub's own auth (client forwards its own token). SC-004 asserts no `apiToken` in rendered output. No concern.

### 4d. Performance & Scalability
- N/A — config-only Driver. Load + render are sub-second, exercised in unit tests.

### 4e. Testing Strategy
- **E1 (💡)**: With E2E owner-skipped, the unit tests assert the manifest/render contract but **not** that the manifest produces a working deployment against the real chart. The deserialize/render assertions hardcode chart coordinates (`oci://.../infrahub-mcp` v`0.1.0`) and the selector label (`app.kubernetes.io/name: infrahub-mcp`) that are still *unconfirmed* (the PRD Open Question). If those are wrong, tests stay green while a real deploy fails. **Mitigation already in plan/research R5**: verify both against the published chart `templates/` before finalizing the manifest. Keep this as an explicit implementation task (it will surface in `tasks.md`). Acceptable given the owner-approved tradeoff.

### 4f. Operational Readiness
- N/A — no migrations, no rollout strategy beyond standard Driver loading. Driver is independently versionable (`supported_versions`).

### 4g. Dependencies & Integration Risks
- **E2 (🤔→tracked)**: New upstream dependency (the `infrahub-mcp` Helm chart + image) is owner-approved. Residual risk: the chart may not yet be published at the assumed OCI path/version. This is the same Open Question as E1's coordinates; resolved by implementation-time verification, does not block design.

## Cross-Lens Insights

- **X1 (💡)**: E2E-skip (engineering) × "does it actually deploy for the operator" (product) converge on the *unconfirmed chart coordinates/selector* as the single point where automated coverage is thinnest. The agreed mitigation — verify coordinates + selector label against the real chart during implementation, before the deserialize test is finalized — covers both lenses. Already reflected in research R5 and the plan; ensure `tasks.md` makes it an explicit, ordered task gating the manifest write.
