# Critique Report: Configurable Backup Retention TTL

**Feature**: 016-backup-retention-ttl | **Date**: 2026-08-03 10:49 | **Artifacts reviewed**: spec.md, plan.md, research.md, data-model.md, contracts/graphql-delta.md, quickstart.md | **Constitution**: v1.4.1

## Executive Summary

The spec and plan are strong: the feature is tightly scoped, sourced from a real gap (issue #305), rides an established codebase pattern (ADR-029) with zero migration, and the test strategy maps every FR to a concrete suite with the E2E extending an existing `shard_backup` node ("reuse before you boot"). Two must-address findings surfaced, both engineering-verifiable against the code rather than matters of opinion: (M1) the frontend **environment** configuration tab has its own full-replacement input builder (`buildFullReplacementInput` in `EnvironmentConfigurationTab.helpers.ts:98`) that the plan missed — without carrying `backup_ttl` through it, any env-var edit from the UI silently wipes the stored policy, defeating FR-005 for the most likely scope; and (M2) the planned `metadata_updates` merge writes to a plain SQLAlchemy `JSON` column, where in-place dict mutation is not change-tracked — the plan must pin reassignment semantics or the audit metadata silently never persists. Both are small, localized fixes to plan/research (and one clause in spec FR-005). Verdict: **⚠️ PROCEED WITH UPDATES** — fixes applied in this run (autonomous mode), then `/speckit-tasks`.

## Product Lens Findings

### 3b. User Value Assessment
- US1 (environment policy) is a genuine standalone MVP; priorities are coherent (validation and visibility ride on it).
- **P1 (💡)**: There is no first-party *setter* UX: the web UI environment form only edits env vars (scalars are carried through unchanged), and the CLI has no `environments update` command. Setting `backup_ttl` therefore happens via GraphQL/SDK (or a CLI deployment manifest for deployment scope). This matches the PRD's deliberate frontend scope (visibility only), but the docs' new Retention section MUST include a concrete "how to set it" GraphQL example, or SC-001 ("zero out-of-band edits") reads hollow to an operator who can't find the knob. → Addressed by extending the R10 docs decision.
- **Q1 (🤔, resolved)**: Should the environment UI gain an editable `backup_ttl` field? **Resolution: No** — PRD explicitly scopes the frontend to the expiry column; preservation (not editing) is the UI obligation. Revisit on demand.

## Engineering Lens Findings

### 4a. Architecture Soundness
Layering is clean (config validates, workflow resolves, builder renders, GraphQL exposes) and matches §III. One gap:

- **E1 / M1 (🎯 Must-Address)**: **Frontend environment full-replacement builder missed.** `frontend/src/pages/environments/EnvironmentConfigurationTab.helpers.ts:98` (`buildFullReplacementInput`) hand-assembles `UpdateEnvironmentInput` from the persisted config, field by field. The plan covers the deployment-side round-trip (`lib/deployment-input.ts`) but not this builder. Once `backupTtl` exists on `UpdateEnvironmentInput`, any env-var save from the UI omits it → full-replacement semantics clear the stored environment policy. This violates FR-005's intent on the *primary* scope (environment) via the *primary* client (web UI), and it is silent data loss — the exact failure class FR-005 exists to prevent. **Fix**: carry `backup_ttl` through `buildFullReplacementInput` (string scalar pass-through, like `dbSize`); extend its unit coverage (`EnvironmentConfigurationTab.test.tsx` / helpers test) with a preservation assertion; list the file in plan.md Project Structure and research R7; add a clarifying clause to spec FR-005.

### 4b. Failure Mode Analysis
- TTL resolution isolated from the BSL try/except (research R3 caveat) — good.
- **E2 / M2 (🎯 Must-Address)**: **JSON column change-tracking pitfall.** `Backup.metadata_` is a plain `Column("metadata", JSON)` (no `MutableDict`). The planned `update_backup_status(metadata_updates=...)` must **reassign** the attribute (`backup.metadata_ = {**(backup.metadata_ or {}), **updates}`), never mutate in place, or SQLAlchemy will not detect the change and `ttl`/`ttl_source`/`expires_at` silently never persist — FR-006/FR-007 would pass unit tests that inspect the object yet fail propagation/E2E. Must be pinned in research R5/data-model so the tasks encode it and the propagation test reads back through a fresh session.
- **E3 (💡)**: **E2E fanout race.** Updating the scenario environment's config triggers the standard redeploy fanout (new instance version, Helm-level no-op) on a *session-shared* environment. The extended E2E must (a) set `backup_ttl` and wait for the fanout/deployment to return to steady state before creating the backup, and (b) be conscious that the policy persists on the shared environment for subsequent tests in the session (no current test asserts a TTL, so this is benign today — but the wait is required to avoid flaking the definition-of-done gate). Encode in the E2E task.
- Velero unavailable / backup fails → no `status.expiration` → null → "—": already specified.

### 4c. Security & Privacy — no findings
Operator-supplied string, strictly regex-validated before persistence, rendered into a typed K8s field; no secrets, no PII, no authz change.

### 4d. Performance & Scalability — no findings
One dict lookup per backup creation; two nullable fields on existing queries.

### 4e. Testing Strategy
Comprehensive and FR-mapped. Two sharpening notes:
- **E4 (💡)**: The `Backup.ttl`/`expiresAt` propagation test must read through a **fresh session/UoW** (DB round-trip), not the in-memory object, to actually catch M2-class bugs. Also cover `metadata_ = None` (pre-existing rows) → both fields null.
- The env-input schema-walking guard mechanically forces the `UpdateEnvironmentInput` addition — good; the deployment-side introspection suite (`test_update_deployment_input_introspection.py`) should get the equivalent `backup_ttl` entry if it enumerates fields explicitly.

### 4f. Operational Readiness
Resolved-TTL + source-scope logging covers US10; rollback is trivially safe (nullable additive fields; unset config = today's behaviour). No migration to reverse. No findings.

### 4g. Dependencies & Integration Risks
No new dependencies. Velero contract (`spec.ttl`, `status.expiration`) is its documented stable API. SDK/CLI pick the fields up via regeneration; CLI deployment manifests validate against the regenerated `UpdateDeploymentInput` (`_build_update_input`, `deployments.py:175`) so `backupTtl` in a manifest works with zero CLI changes — and manifest omission clearing the value is *correct* declarative semantics there (the manifest is the declared state). No findings.
