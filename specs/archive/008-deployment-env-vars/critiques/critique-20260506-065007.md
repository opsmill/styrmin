# Critique: Deployment Env Vars (Free-Form, Post-Render Injected)

**Date**: 2026-05-06
**Spec**: [`spec.md`](../spec.md)
**Plan**: [`plan.md`](../plan.md)
**Reviewers**: Product Lens (CEO/PM mindset) · Engineering Lens (Staff Engineer mindset)

## Executive Summary

The spec is well-grilled (came out of `/grill-with-docs` against issue #4) and the plan rides on the existing scheduling resolver / post-render injection plumbing — the lowest-risk path. The dual-lens review surfaces **two must-address issues** (one product-scope question, one engineering-correctness gap), **three recommendations**, and **two questions** that benefit from explicit acknowledgement in the artefacts. None of the findings are architectural showstoppers; the feature can proceed to `/speckit.tasks` after the must-address items are applied.

**Verdict**: ⚠️ **PROCEED WITH UPDATES** — fixes will be applied inline before tasks generation, per the auto-prep workflow.

## Engineering Lens Findings

### 4a. Architecture Soundness
Reuses established patterns: `EnvVarsResolver` mirrors `SchedulingResolver`, `build_env_vars_post_rendering_patches` mirrors `build_scheduling_post_rendering_patches`. Layer boundaries are clean. No coupling concerns.

### 4b. Failure Modes
- **🎯 E1 (must-address)**: The size caps are defined per-scope (100 entries / 256 KiB per scope, 64 KiB per value) but **no aggregate cap on the resolved per-component dict** is defined. A merged dict can in principle approach 3× a single-scope's bytes (env + dep + comp at full cap) plus driver-rendered chart env values. Combined with the deployment CRD context-embedding (ADR-006) and Kubernetes' 1.5 MiB resource size limit, this is a real risk for deployments with many large env vars across many components. Spec FR-008 needs an additional invariant on the *resolved* dict.
- **🎯 E2 (must-address)**: Plan §1.3 says env vars merge into the per-component config block via `ArbitrarySectionModel.env_vars`. There are **two** `ArbitrarySectionModel` classes (one in `context/models/components.py`, one in `services/driver/models/resources/driver.py`) — the plan needs to specify which class owns the field, and the data-model needs to be explicit that the *driver-side* class is unaffected (driver components can't carry user env vars; that's the documentation-only `DriverEnvVarDoc` path).

### 4c. Security & Privacy
- **💡 E3 (recommendation)**: PATH / LD_* family is documented as "risky" but not validated. A `logger.warning("env_var_potentially_risky_name", name=...)` at validation time (not a rejection) is cheap and creates an audit trail when an operator unintentionally clobbers loader behaviour. Recommended.
- The "users putting credentials here is unsupported and unsafe" warning has no API-side surface in v1 (UI is out of scope). The SDK/GraphQL field description on `EnvVar.value` is the only available channel — already implied in contracts §1 but worth making explicit.

### 4d. Performance & Scalability
- The 1.5 MiB CRD limit is a real constraint that's not currently called out in research.md as the *reason* the size caps exist. Tying the caps to a concrete constraint helps future maintainers reason about them. (Recommendation E4.)

### 4e. Testing Strategy
Six unit bundles + propagation + E2E is appropriate. The propagation matrix in `contracts/graphql.md` §4 maps each new field/argument to one assertion — meets Constitution §V exactly. ✅

### 4f. Operational Readiness
Structured `logger.warning` for collisions is correct. No metrics planned, which is fine for v1.

### 4g. Dependencies & Integration
No new dependencies. Integration touches three existing systems (config resolver, post-render injection, driver loader); each is a well-known seam. No risk flags.

## Cross-Lens Insights

- **🤔 X1 (question)**: Driver-side env var documentation (US4) and orphan tracking (US5) ship in v1 but the UI surface that consumes them does not. From the product lens, value-capture is partially deferred. From the engineering lens, the cost of including them now is small (the driver loader and resolver have to know about them anyway). **Decision**: keep both in v1 — deferring would split the implementation across two features and force the loader/resolver work to live on a half-finished branch. This is captured in the spec; the critique flags it as a known asymmetry rather than a defect.
- **🤔 X2 (question)**: The plan piggy-backs collision warnings onto the existing `DeploymentTimelineEntry` (extending it with `envVarCollisions`). The deployment timeline is currently a derived view — adding a structured field to it is the lightest path, but operators may expect a dedicated "warnings" surface. **Decision**: document the choice in plan.md research §4 (already done) and accept it. A dedicated warnings table is deferred until more event types accumulate.
