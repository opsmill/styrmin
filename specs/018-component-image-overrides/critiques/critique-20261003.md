# Critique Report: Per-Component Image Overrides via Post-Render

**Date**: 2026-10-03
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

The spec follows the idea brief closely, and the plan reuses ADR-057's mechanism. The hardest
dependency gap, a post-render patch that must never add a container, was solved with the
dependency's own extension point and checked against kustomize v5.7.1 before design. Two items must
be fixed before tasks.

1. **The operator would miss the guard failure on updates (E1).** After a spec update the operator
   keeps the `HelmReleaseReady=True` condition from the previous rollout. Its timer therefore
   advances straight to `Ready` without reading the new HelmRelease. A guard failure on an existing
   deployment (User Story 1's flow, and E2E test 3) would show "Running" while the HelmRelease is
   failed. This breaks FR-007 and SC-005.
2. **The spec and plan disagree on upgrade validation (E2).** Plan D-008 re-validates stored
   overrides in `updateDeploymentVersion`, but the spec's FR-009 and User Story 4 Sc.5 say only
   "render fails".

Both have local fixes. The recommendations cover where the Kustomize-semantics tests run (CI's unit
job has no `kubectl`), proving SC-002 with a test, rollback safety (`extra="forbid"` on older
platforms), and three documentation gaps users will hit: image pull failures, mutable tags under
`IfNotPresent`, and apply races.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | `kopf_on_styrmin_deployment_update` keeps the existing conditions, so after an update `HelmReleaseReady` is still `True`. The timer's `CREATING_HELM_RELEASE` branch then skips `_check_helmrelease_ready` and moves to `Ready`. D-004 only reads the HelmRelease in that branch, so a guard failure on an existing deployment is never seen. `_check_helmrelease_ready` also ignores generation, so a stale `Ready=True` from the previous revision would be trusted. | Revise D-004: in the timer, for phases `CREATING_HELM_RELEASE` **and** `READY`, read the HelmRelease. When its `Ready` condition is `False`, its `observedGeneration` equals `metadata.generation`, and a condition message carries the guard key, fail the deployment with `COMPONENT_CONTAINER_NOT_FOUND`. Do not change the general readiness flow (resetting conditions on update would trip the creation-timestamp-based 300 s timeout on every update). Visible within one or two timer intervals (60 s). |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E2 | 🎯 | Plan D-008 adds an up-front check in `updateDeploymentVersion`. Without it, the driver's upgrade action stops `server` before the render fails. The spec's FR-009, User Story 4 Sc.5 and the edge case still describe a render-only failure. | Update the spec: FR-009 adds "a version change that would make a stored, applicable reference invalid after substitution MUST be rejected before any task starts, with the same typed error"; User Story 4 Sc.5 and the edge case say so too. |
| E3 | 💡 | helm-controller versions may report the post-render error under `Ready` or `Released`, possibly reworded. | Match the guard key in any HelmRelease condition message, not only `Ready`'s. The key is in the op path, so it survives rewording. |
| E4 | 💡 | `styrminctl apply` with an override change and a version change in one manifest: the config task writes the CR, then the upgrade action may read the pre-override workload, so its Job uses the chart image's repository. Env vars have the same race. | Document it in the apply docs: set the override and reconcile before upgrading, or accept that the first upgrade Job uses the previous image repository. |
