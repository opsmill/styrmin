## Executive Summary

The problem is real and visible in the code: the operator reports updates `Ready` before FluxCD applies them, so a task can show success while its HelmRelease fails, and nothing records command output. The plan finds that root cause and fixes it (research D5) instead of only displaying what exists. Five gaps must be fixed before tasks are generated:

- The plan treats FluxCD's `Remediated=True` as a final failure. FluxCD remediates after each failed attempt and then retries, so a CR could stay `Failed` after a later attempt succeeds.
- The task result rules do not handle tasks that one hook started superseding each other. In every normal upgrade of the bundled drivers, the upgrade's result and the planned E2E assertion would be wrong.
- The timeline reads steps through per-object GraphQL resolvers, and Styrmin has no data loaders, so a 50-task timeline would run about a thousand queries every 10 seconds per viewer.
- Velero's `FailedValidation` phase is not terminal in `poll_restore_status`, so the planned failed-restore E2E would wait two hours.
- Every `apply_state` task has the type `noop`, so users cannot find "the upgrade" that the P1 acceptance scenario names.

All five are local fixes. The recommendations tighten the operator contract on resume, the failed-then-succeeded path of operator steps, the access to `recordStep`, a race between the plan step and the task row, and the E2E design.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | Research D5 step 4 and [contracts/operator-status.md](../contracts/operator-status.md) set the CR `Failed` when FluxCD's `Remediated` is `True`. With `upgrade.remediation.retries: 3` (`builders/application.py:231`), FluxCD rolls back after each failed attempt and then retries. If attempt 2 succeeds, the CR stays `Failed` because the timer does nothing for that phase. | Only `Stalled=True` for the current generation is final. `Remediated=True` sets `rolledBackAt` and `rollbackMessage` on the HelmRelease step and ends the current attempt, nothing more. The readiness timeout stays the safety net. |
| E2 | 🎯 | The task result rules (research D8, data-model) do not handle tasks started by the same hook. In the simple-app upgrade, `stop_components` and `upgrade_deployment_version` each write the CR before the previous rollout ends, so the next started task supersedes them. Rule 4 of D8 ("every started task succeeded") then never gives the upgrade `SUCCEEDED`. A task outside the upgrade that interrupts the last started task does not make the upgrade `SUPERSEDED`. The planned E2E assertion "the upgrade and its started tasks are `SUCCEEDED`" would fail. | Calculate over the task's family: the task and the tasks its hook steps started, transitively. `RUNNING` if a family step is pending or running; `FAILED` if a family step failed; `SUPERSEDED` if a family step was superseded by a task outside the family; `SUCCEEDED` otherwise. Each started task on its own still shows `SUPERSEDED` when a sibling interrupted it. Add the case to the spec's edge cases and fix the E2E assertion. |
| E3 | 💡 | Research D5 lists the resume handler with create and update for resetting `HelmReleaseReady` and recording `status.rolloutStartedAt`. A resume continues a rollout; resetting the start time would extend the readiness timeout after each operator restart. | Resume writes `status.instanceId` and sets `rolloutStartedAt` only when it is missing. Only create and update reset `HelmReleaseReady`. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E4 | 💡 | After the readiness timeout fails the HelmRelease step, FluxCD can still succeed on a retry and the operator moves on to `Ready`. The contract says a step moves to `running` only on a new report for its own phase, so a failed HelmRelease step followed by a `CreatingServices` report is undefined. | When a report shows a later phase, every earlier `failed` operator-phase step gets a new attempt and succeeds. |
| E5 | 💡 | `apply_state` dispatches the flow before the caller commits the task row (`services/reconciliation/__init__.py:84`, `services/primitives.py:144-151`). The flow can try to record "Plan the changes" before the row exists. The callback already tolerates this race by returning `success: false`. | The plan-step write retries on `TaskNotFoundError` for up to 10 seconds, then logs and continues. |
| E6 | 🎯 | `poll_restore_status` and `poll_backup_status` return only on `Completed`, `PartiallyFailed` and `Failed` (`velero/client.py:253, 272`). A restore of a backup that Velero cannot find ends in `FailedValidation` and is polled until the 7,200-second timeout. The planned failed-restore E2E would hang. | Treat `FailedValidation` as terminal in both functions; the restore step fails with Velero's validation errors. In the E2E, remove the Velero backup with a `DeleteBackupRequest` and wait for the `Backup` object to disappear, so Velero's backup sync does not bring it back. |

### Performance & Scalability

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E8 | 🎯 | Styrmin's GraphQL resolvers query per object (`api/resolvers.py:13`); there are no data loaders. The timeline asks for `Task.steps`, `Task.result`, `Step.supersededBy` and `Step.startedTasks` for every task and step. For 50 tasks with 10 steps each, that is roughly a thousand queries per refresh, every 10 seconds, per open page. The plan claims three queries without saying how. | The timeline service builds a read model: steps for all tasks, started tasks per step, superseding task summaries, family results and the deployment's last report time, in three queries. The GraphQL `Task` and `Step` objects carry it in `strawberry.Private` fields, and their resolvers query only when it is absent (single-task reads). A unit test counts the queries of a timeline read. |
| E9 | 💡 | The phase history runs for every deployment on every 5-second report. | Return early when the task's operator-phase steps are all final, before locking rows. |
