# Critique Report: Environment-Level Backup and Restore

**Feature**: `specs/001-env-backup-restore` | **Date**: 2026-08-06 | **Artifacts reviewed**: spec.md, plan.md, research.md, data-model.md, contracts/graphql.md, quickstart.md, constitution v1.4.1

## Executive Summary

The spec and plan are unusually well-grounded: the problem is validated by issue #7 and a pre-hardened brief, every design decision cites a concrete codebase mechanism, and the reuse constraint (zero changes to the per-instance Prefect flows) is honored throughout. Two engineering findings are **Must-Address** — both are interaction gaps with existing machinery rather than architecture flaws, and both are resolvable with small spec/plan edits: (E1) environment deletion is a bare row delete today and would violate the new FK, and (E2) a constituent stuck in `PENDING` would pin the derived parent status and deadlock the environment-level concurrency guard unless deletion is guaranteed to work as an escape hatch. Verdict: **⚠️ PROCEED WITH UPDATES**.

## Product Lens Findings

### 3a. Problem Validation — strong, no findings

Issue #7 documents the operator pain directly; the grilling interview pinned membership, status semantics, restore contract, and lifecycle before the spec was written. Scope is well-carved (clone deferred to P2 with clone-readiness preserved via FR-003).

### 3b. User Value Assessment

- **P1 (💡)** — The role asymmetry is invisible in the spec: per-instance restore is `READ_WRITE`, but environment restore will be `ADMIN` (it reverts environment config — research.md D7). An operator who can restore every application individually may be surprised the coordinated button is gated higher. The reasoning is sound (privilege parity with `updateEnvironment`); the spec should state it so the frontend gates the action correctly and docs can explain it. *Suggestion: add to spec Assumptions; note the `ADMIN` gate on the restore action in FR-012.*

### 3c. Alternative Approaches — no findings

The "no parent record, just filter per-instance backups by label" alternative was already rejected by the issue itself (traceability is the requirement). Reuse-not-rebuild is the design's spine.

### 3d. Edge Cases & User Experience

- **P2 (💡)** — FR-007's skip-reason list omits a restore-time conflict: a constituent whose deployment is already `RESTORING` (from an individual restore started moments earlier). `create_restore` raises `RestoreAlreadyInProgressError` in that case; without a defined outcome this becomes either a mutation failure (wrong — violates the never-abort spirit) or a silent skip (violates FR-007). *Suggestion: add "deployment busy with another restore" to the uniform skip reasons in FR-007, the edge cases, and data-model.md.*

### 3e. Success Measurement — no findings

SC-001…SC-006 are measurable and technology-agnostic; SC-003's property formulation ("no stored parent status can contradict constituents") is directly testable and the derived-status design makes it true by construction.

## Engineering Lens Findings

### 4a. Architecture Soundness

- **E1 (🎯)** — **Environment deletion vs. environment backups is undefined.** `delete_environment` (`backend/styrmin_backend/services/environments.py:396-405`) deletes the row with no dependent-row handling. With the new `environmentbackup.environment_id` FK, deleting an environment that has environment backups raises an FK violation, which `StructuredErrorExtension` masks as `INTERNAL_ERROR` — a crash, not a behavior. *Suggestion: spec a new FR — deleting an environment deletes its environment backups (and their environment restores) via the same cascade as `deleteEnvironmentBackup`; note in data-model.md and plan structure (touches `services/environments.py`). v1 keeps snapshots environment-bound; the P2 clone spec may revisit snapshot survival.*
- **E3 (💡)** — Reverting to a captured config of `None` cannot go through `update_environment`: that service treats `config is None` as an idempotent no-op (`services/environments.py:296-302`). The restore path must set `Environment.config` directly (with capability recomputation and the exclusion-aware fan-out from D4), not delegate to `update_environment`. *Suggestion: amend research.md D4 to name this explicitly so the implementer doesn't reuse the wrong entry point.*

### 4b. Failure Mode Analysis

- **E2 (🎯)** — **A constituent stuck in `PENDING` deadlocks environment-level operations.** Dispatch is fire-and-forget; a dispatch failure or dead worker leaves the `Backup` row `PENDING` forever (no janitor covers backups — ADR-0024's cleanup is scoped to observed-state tables). Derived parent status then stays `IN_PROGRESS`, and the D6 concurrency guard blocks every future environment backup/restore for that environment indefinitely. The per-instance guard has the same failure mode today, but the blast radius here grows from one instance to the whole environment. The escape hatch already implicit in the design — deleting the environment backup — works only if deletion is legal regardless of derived status. *Suggestion: make the escape hatch explicit: FR-010 gains "deletion MUST be possible regardless of the environment backup's derived status"; add an edge case documenting the stuck-constituent scenario and the deletion escape hatch.*
- **E6 (🤔 → resolved)** — The D6 guard race (two concurrent creates both passing the EXISTS check) is already documented as accepted, with per-instance guards downgrading the collision to a `PARTIAL` outcome. No change needed.

### 4c. Security & Privacy — no findings

Roles reuse ADR-0017 (with the D7 ADMIN gate on restore closing the config-mutation bypass). Snapshot JSON contains deployment config/parameters — the same data already visible to the same roles via existing queries; no new exposure.

### 4d. Performance & Scalability — no findings

Sequential fire-and-forget dispatch meets SC-006 with an order of magnitude of headroom; snapshot JSON is KB-scale; derivation queries are per-parent joins over tens of rows.

### 4e. Testing Strategy

- **E4 (💡)** — The "expired" skip classification has a hidden input: Velero GC deletes cluster-side data but never touches the DB row, which remains `COMPLETED`. Classification must compute expiry from the backup's recorded TTL metadata (`expiresAt < now`), exactly as the existing `Backup.expiresAt` resolver does. *Suggestion: one-line note in data-model.md so the unit tests cover an expired-but-COMPLETED constituent.*

### 4f. Operational Readiness

- **E5 (💡)** — ADR-0012 fan-outs emit a structured audit log line with outcome counters (`env_config_fanout_dispatched … evaluated=… dispatched=… skipped_noop=… dispatch_failed=…`). The new fan-outs should do the same (`env_backup_fanout_dispatched`, `env_restore_fanout_dispatched`) for parity and debuggability. *Suggestion: amend research.md D1.*

### 4g. Dependencies & Integration Risks — no findings

No new dependencies; the single CI change is the pre-authorized matrix-exclusion removal; migrations are reversible (D10 defines downgrade; no DB enums involved).

## Cross-Lens Insights

- **X1 (💡)** — Derived status can read terminal while the restore's *config fan-out* is still converging: fan-out redeploys are tracked by `Task` rows, not `Restore` rows, so an `EnvironmentRestore` whose data restores finished (or were all skipped) shows `COMPLETED`/`PARTIAL` while deployments are still redeploying. A backup taken at that moment snapshots mid-convergence. This is consistent with the feature's declared "near-consistent, no quiescing" semantics and with today's per-instance behavior (you can back up during a deploy), but the docs and spec assumptions should say so — a user reading `COMPLETED` will assume full convergence. *Suggestion: one sentence in spec Assumptions + the docs task.*
