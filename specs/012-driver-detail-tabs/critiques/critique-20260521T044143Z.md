# Critique: Driver Detail Page Redesign (Tabbed Layout)

**Feature**: `012-driver-detail-tabs`
**Date**: 2026-05-21
**Reviewer**: dual-lens automated review (Product + Engineering)
**Verdict**: ⚠️ **PROCEED WITH UPDATES** — no must-address findings; six low-risk recommendations applied autonomously.

## Executive Summary

The spec and plan emerged from a structured `/grill-idea` interview and survive both lenses with no must-address blockers. The Constitution Check passes cleanly: only the GraphQL schema gate is crossed (acknowledged), §V E2E and propagation-test obligations are both planned, and no DB or auth surface is touched. Scope is tightly carved into three independently-shippable slices (P1/P2/P3).

The six recommendations below sharpen edge-case behaviour and accessibility without changing scope. All are applied in-place to `spec.md` and the plan-phase artefacts; none warrant deferring to v2 or rethinking the architecture.

## Product Lens Findings

### 3a. Problem Validation

The problem statement is concrete (raw-JSON dumps + all-versions-at-once-scroll on the existing page) and the user (platform engineer maintaining the driver catalogue) is well-named. Internal tooling does not require external user-research evidence; the pain points are observable in the current code. No findings.

### 3b. User Value Assessment

All three user stories deliver tangible value and ship independently. Acceptance criteria are written in Given/When/Then user-outcome form. MVP analysis is built into the carve: P1 = left rail + tabs scaffold + Overview + Parameters; P2 = Components + Actions; P3 = Source. No findings.

### 3c. Alternative Approaches

The "simpler" alternative — leaving the existing page as-is and reformatting the JSON dumps inline — was implicitly rejected in the grilling phase because it scales poorly with version count (the primary pain). The chosen approach matches the established sibling page (`DeploymentDetailPage`), avoiding net-new patterns. No findings.

### 3d. Edge Cases & User Experience

- 💡 **P1 (accessibility)**: the spec does not call out keyboard navigation. Version rows must be focusable / activatable via keyboard; the existing `<Tabs>` primitive already handles tab keyboard nav. Recommendation: add an FR that version rows are `<button>` elements (focusable, Enter/Space-activatable) and the active row uses `aria-pressed` or equivalent.
- 💡 **P2 (Overview-tab empty fields)**: `FR-017/018/019/020` cover empty Parameters/Components/Actions/versions, but the Overview tab synthesises a summary across those same fields. If a driver version has `parameters: []` and `actions: []` and `components: null`, the Overview tab still renders three summary tiles (helm chart, components, parameters) with potentially "0" or "—" values. Recommendation: Overview tab tiles must show meaningful empty states ("No components declared") rather than blanks.
- 💡 **P3 (long version labels)**: `version` is a free-form string. The left rail must not overflow when a driver uses a long version like `2026.05.21-rc1-hotfix-cherry`. Recommendation: the rail row truncates with ellipsis and exposes the full value via `title`/`aria-label`. (Implementation-level; surfaced here for completeness but already implied by the "no internal scrolling region" rule.)

### 3e. Success Measurement

`SC-001`–`SC-005` are measurable and technology-agnostic. `SC-005` says "typical engineering laptop" which is fuzzy but acceptable as a UX threshold; the rest are tight. No findings.

## Engineering Lens Findings

### 4a. Architecture Soundness

Component split (~7 components + 5 tab panels) is reasonable; existing primitives are reused; layered architecture is unaffected. The plan correctly identifies that the GraphQL change is a thin resolver projection. No findings.

### 4b. Failure Mode Analysis

- 💡 **P4 (auto-refresh error behaviour)**: today the page handles `error` from `useGetDriverQuery` by replacing the entire view with `<ErrorState>`. If an auto-refresh poll fails mid-session, the page is destroyed even though the previous snapshot is still valid. The current spec preserves this behaviour by saying "query failures continue to flow through the existing `ErrorState` component" — which is consistent but suboptimal. Recommendation: at minimum, document this as a known limitation (not a regression); flag for a follow-up if a future spec wants resilient polling.
- ✅ EC-002 (selected version disappears mid-session) is covered.
- ✅ EC-004 (malformed `components` JSON) is covered.

### 4c. Security & Privacy Review

No new auth surface; existing `IfRole minimum="READ_WRITE"` gating is preserved. `sourceRepository` is already visible on the current page (no new disclosure). No findings.

### 4d. Performance & Scalability

`useGetDriverQuery` pulls all versions and their nested fields in one round-trip. For drivers with many versions × many parameters, payload size could grow, but the spec bounds itself to 20 versions and there is no current evidence of multi-hundred-version drivers in practice. No must-address item; no recommendation worth applying.

### 4e. Testing Strategy

`research.md §9` lists coverage targets and includes the silent-fallback case implicitly via the page-level test. Adding it as a named test case removes ambiguity.

- 💡 **P5 (test enumeration)**: list `EC-002 silent-fallback` as a named unit test case in research.md to remove ambiguity for the implementer.

### 4f. Operational Readiness

- 💡 **P6 (deploy/rollback)**: no feature flag is planned; the frontend rewrite ships as part of the next bundle deploy and a regression is recovered by reverting the commit. This is the right call for a UI-only redesign but worth noting in research.md so reviewers don't ask "where is the kill switch?".

### 4g. Dependencies & Integration Risks

- 💡 **P7 (SDK additivity)**: `createdOn` is additive on the GraphQL schema. Existing SDK consumers that don't select `createdOn` will not see the field in their generated Pydantic models (ariadne-codegen generates per-operation types). The regenerated SDK files will pick up the field only where its underlying operation requests it. Worth a one-line note in research.md so reviewers don't suspect a breaking-change ripple.

## Cross-Lens Insights

- **Scope discipline holds**: both lenses converged on "the scope is tight". The "no placeholders" decision in the grill phase reduces both UX clutter (Product) and code complexity (Engineering).
- **Empty-state matrix is the main softness**: FR-017–020 cover the obvious holes, but the Overview tab and the long-version-label cases are corner-of-corner edge cases that both lenses flagged (P2, P3). Worth a single sweep through the spec.
- **No deferrals warranted**: every recommendation is small enough to apply now without rethinking the spec or plan.
