## Executive Summary

The spec follows the PRD closely and the plan reuses the environment update's mechanisms (commit order, per-deployment comparison, `redeploy_for_environment_update`, the #252 teardown path) instead of adding new flows or tables. The resolved-config comparison (D1) is the right rule for "environments that override the value are not redeployed". Three findings must be fixed before tasks are generated. First, the controller decision table decides per controller state, so a resubmission after a failed turn-on moves the applications onto a failed controller, which contradicts the spec's own edge case. Second, the removal rule can request the deletion of a controller whose creation flow has not written its StyrminDeployment yet, which can leave a controller running with no database row behind it. Third, the state-based removal rule and the `RUNNING` hook also act after an environment update, a behaviour change that the spec does not state. The remaining findings improve the administrator's journey (getting the current config as JSON, a clearer CLI result) and observability.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | D4 decides the application action from the controller state only. Row "Set, `FAILED`, same values → redeploy now" moves applications that were on the shared class onto a failed controller when the administrator resubmits after a failed turn-on. The spec's edge case says they stay on their current config and stay reachable. | Decide per application. An application whose `dedicated_ingress` changes (moves onto the controller, or the controller's values change) is redeployed only when the controller is `RUNNING` with the new values; otherwise it waits. Every other application is redeployed now, whatever the controller state (this keeps the Clarifications rule for applications already on a failed controller). A `FAILED` controller with waiting applications is redeployed again (retry). Update research D4, data-model §4, the spec Clarifications and the edge case. |
| E2 | 🎯 | Since the new `RUNNING` hook and the extended removal rule are state-based, they also act after `updateEnvironment`: a controller that becomes `RUNNING` runs its environment's fan-out, and an environment update that turns `dedicated_ingress` off at environment level now removes the controller after the applications move. The spec says nothing about this change to the environment update. | State it in the spec (edge case) and in research D5, and include it in the documentation tasks. The new environment behaviour is the correct order, so no code restriction is needed. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 🎯 | The removal rule (D5) can run while the controller is `PENDING` or `DEPLOYING` (turned off right after it was created). `_patch_deletion_requested` finds no StyrminDeployment yet, the row goes to `DELETING` and is tombstoned, and the `apply_state` flow, which does not check for `DELETING`, then writes the StyrminDeployment: a controller runs on the cluster with no live row. | Add "the controller is not `PENDING` or `DEPLOYING`" to the removal rule, and run the removal check when an internal deployment moves to `RUNNING` or `FAILED`. |
| E4 | 💡 | The continuation runs inside a savepoint, but `apply_state` dispatches a Prefect flow before the commit. If the savepoint rolls back, the dispatched flow refers to a task row that was never committed. | Keep the per-deployment `try/except` around each redeploy start (as in `update_environment`) so that a dispatch failure never reaches the savepoint; the savepoint only catches unexpected errors. Record the remaining window in research D7. |
