# Dual-Lens Critique — Feature 013 (Driver Reload Identity / Provenance Fingerprint)

**Timestamp**: 2026-05-25T10:29:21Z

## Executive Summary

The spec and plan are unusually well-shaped because they came out of a structured grilling session (`/grill-idea`) before specification. Vocabulary aligns with `CONTEXT.md`; constitution gates all pass; the design is minimal and surgical. Two areas warrant attention before tasks generation:

1. **§V E2E coverage of the git path** — the plan defers git-path coverage to a unit test against a mocked provider. Per Constitution §V, skipping E2E for *new feature behaviour* requires explicit reviewer approval; the implementer cannot decide unilaterally. The decision was made during grilling (with the project owner acting as reviewer), but the spec/plan don't capture that approval in a discoverable way. Fix: record the approval explicitly so future reviewers can audit the decision.
2. **Concurrent-reload race window** — without a DB-level UNIQUE constraint over the identity tuple, two parallel loads of the same content can race past the lookup-then-insert pattern and produce two duplicate rows. The plan acknowledges this but defers the index to "implementation discretion". Recommendation: lock it in at plan time so it isn't quietly dropped during implementation.

Verdict: **⚠️ PROCEED WITH UPDATES**. One must-address item (M1) with an auto-applyable fix; two recommendations.

## Product Lens Findings

### 3a — Problem Validation

The seed (issue #262) is concrete: a real developer hit `IntegrityError` mid-iteration and reported it with a full traceback and a code-line pointer. The "silent overwrite on same-version reload" gap is detected from the same workflow. No alternative interpretation needed.

### 3b — User Value Assessment

P1 stories (local reload, git reload, cascade fix) each deliver value independently. P2 (UI/CLI label) is correctly deferred-in-priority but bundled in scope to avoid the awkward "data model is correct but surfaces are ambiguous" state. MVP analysis: shipping just the cascade fix would be a degenerate version — it removes the crash but keeps the silent-overwrite design gap. Bundling is justified.

### 3c — Alternative Approaches

Grilling considered single polymorphic column, sequence numbering vs short fingerprint, hash-the-parsed-model vs raw-bytes — all rejected with rationale captured in `research.md`. No alternative simpler enough to bring back.

### 3d — Edge Cases & UX

Spec covers: concurrent reloads, identical content at different paths, identical commits across branches, orphan `actions.py`, whitespace-only edits, non-hashed file edits, source-type extensibility. Coverage is thorough.

**P-EDGE-1 (💡 Recommendation)**: the spec asserts "Concurrent reloads of the same content … MUST converge on a single row", and the plan delegates this to "DB transactional guarantees + lookup-then-insert". Without a UNIQUE constraint, two concurrent loaders can both observe "no row" before either inserts, producing duplicate rows. This will be rare but is correctness-affecting. See **E-ARCH-1** (cross-lens).

### 3e — Success Measurement

SC-001..SC-006 are measurable, technology-agnostic, and traceable to user stories. SC-002 (the "no in-place mutation" invariant) is particularly load-bearing for downstream features that depend on `ApplicationInstance.application_driver_version_id` preserving provenance.

## Engineering Lens Findings

### 4a — Architecture Soundness

Layering: hash computation in `services/driver/hash.py` (new, pure), invocation from `services/driver/loaders.py`, repository extension in `repository/application_driver_version.py`, GraphQL exposure in `api/definitions/application_driver/model.py`. No cross-layer shortcuts. Follows the project's established pattern.

**E-ARCH-1 (💡 Recommendation; cross-lens with P-EDGE-1)**: add a database UNIQUE index over `(application_driver_id, source_type, source_repository, source_branch, source_path, version, content_hash, source_commit_sha)` (with `IS NOT DISTINCT FROM`-semantic nullability per Postgres) to close the concurrent-reload race. The plan currently says "deferred to implementation discretion" (research.md D-004); lock it in here so it isn't silently dropped. Cost: one schema line in `db/models.py`. Benefit: eliminates a full class of race-condition bugs without service-layer locking.

### 4b — Failure Mode Analysis

- Hash computation: cannot fail in a meaningful way (raw bytes in, hex out). Confirmed.
- Git commit resolution: `dulwich.repo.Repo(temp).head().decode()` can fail if the cloned repo is in an unusual state (detached HEAD, empty refs). `DriverLoadingError` chain catches this. ✓
- Missing values template: existing loader-level `fail_on_not_found` handles. ✓
- `actions.py` declared but file missing: existing validator path raises before hash is reached. ✓

### 4c — Security & Privacy

No new attack surface. Two read-only scalar fields; no inputs accepted from clients. No PII. No auth model change.

### 4d — Performance & Scalability

SHA-256 over three small files (~few KB each) is sub-millisecond. The new column adds two strings to every `ApplicationDriverVersion` row read; negligible. No new query patterns introduced.

### 4e — Testing Strategy

- Unit: `test_hash.py` (canonical determinism, framing), `test_loaders_fingerprint.py` (populates per `source_type`).
- Propagation: `test_application_driver_version_propagation.py` (mandatory per §V for both new read fields).
- Service-layer: `test_applications_upsert_idempotent.py`.
- E2E: `test_driver_reload_identity.py` (`shard_readonly`, `api_only`, `ci`). Local path only.
- Frontend: component test for `<version>@<short>` label.

**E-TEST-1 (🎯 Must-Address; cross-lens with the Constitution §V gate)**: the plan covers git-path behaviour with a unit test against a *mocked* git provider. Per Constitution §V, "New features MUST ship with an E2E test that covers the user-visible flow end-to-end" and "Deferring E2E coverage to a follow-up, gating it behind 'we'll add it later', or relying on unit/integration tests alone is not acceptable for net-new functionality." A reviewer (the project owner) may approve a skip, but the approval MUST be recorded — implicit-by-grilling is not auditable. **Fix**: add an explicit "E2E coverage decisions" subsection to `plan.md` that records (a) the local-path E2E that is shipping, (b) the git-path decision (skip in v1, covered by mock-provider unit test), and (c) the explicit acknowledgment that the project owner approved this skip during the idea-grilling session. This is the auto-applied fix below.

### 4f — Operational Readiness

- Migration: documented (no Alembic; `metadata.create_all()` on dev DBs).
- Logging: existing driver-load loguru spans propagate.
- Rollback: not applicable — additive schema change with nullable columns; reverting requires only dropping the columns and the cascade kwargs.
- Observability: no new metrics needed. The number of `ApplicationDriverVersion` rows per driver is already queryable.

### 4g — Dependencies & Integration Risks

`dulwich` is already in use. `hashlib` is stdlib. No new dependency. SDK regeneration is the existing ariadne-codegen path.
