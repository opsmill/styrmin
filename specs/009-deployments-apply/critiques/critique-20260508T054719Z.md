## Executive Summary

The spec and plan are well-structured and PRD-grounded. The product story is clear (declarative deployments are a known pain point), the user stories ladder cleanly from P1 (single apply) → P2 (batch + overrides) → P3 (`--wait` + lookup), and the "out of scope" list is unusually disciplined for a v1 — `--dry-run`, declarative deletion, recursive directory traversal, and parallel apply are all explicitly deferred, which keeps the surface area honest.

The architecture is sound: client-side orchestration in the SDK reuses existing `deploy` / `update_deployment` / `update_deployment_version` mutations and adds only one new GraphQL query (`deployment(name, environmentId)`). Layered architecture, type safety, and propagation-test rules from the constitution are all respected.

Three Must-Address findings need fixing before tasks generation:

1. **CLI streaming output under `--wait`** — the contract states the per-deployment line is "replaced" with a `failed` line on terminal failure, which is impossible against an unbuffered terminal stream. Need a clearer two-line-or-buffered model.
2. **PyYAML dependency placement** — `apply_files()` parses YAML in the SDK, so `python_sdk/pyproject.toml` needs PyYAML as a direct dep, not just `cli/pyproject.toml`.
3. **SDK exception base class name** — the contract references `StyrminClientError`, but the actual base is `StyrminError` (verified in `python_sdk/src/styrmin_sdk/exceptions.py`).

A handful of recommendations and questions follow but none block tasks generation. Once the three must-address fixes land, the plan is ready for `/speckit-tasks`.

### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 💡 | Race: two concurrent `apply` runs on the same `(name, environment)` could both read "not found" and both call `deploy`. The DB unique constraint will reject the second one — but the user-facing error will be a generic backend error rather than a friendly "another apply created this concurrently". Spec accepts this in Edge Cases ("concurrent apply OOS") but the error path should still be graceful. | Document that on duplicate-name backend error, `apply()` should re-run the lookup once and switch to update path if the deployment now exists. Otherwise propagate the backend error verbatim. Add to research.md as D2-followup. |
| E4 | 💡 | When `update_deployment` succeeds and `update_deployment_version` then fails (D8 ordering), the deployment is half-updated (new config, old version). Spec accepts continue-on-error, but the user has to know the deployment is in a partial state. | Record this in cli-apply.md: failure messages from the version-upgrade phase should explicitly say "config/parameters were updated; version upgrade failed" so the operator knows. |
| E5 | 🤔 | What if `--wait` times out (network partition, stuck reconciliation)? Today's `deployments create --wait` has a timeout — `apply --wait` should match it. | Decide and document the `--wait` timeout (or "no timeout, user Ctrl-Cs") in cli-apply.md. Suggest matching `deployments create --wait`'s existing default. |
