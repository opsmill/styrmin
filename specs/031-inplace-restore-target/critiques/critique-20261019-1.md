## Executive Summary

The spec follows the PRD closely and the plan puts the rule in one service function, with every caller and client listed. The problem is real and the fix is narrow: no database change, no flow change, no new error code. One item must be fixed before tasks: the spec and the plan describe the breaking change only as "two arguments and one option are removed". They do not say that the form `styrminctl backups restore <backup id> --target-deployment X`, which `cli/README.md` shows as its example today, is now refused, nor that every restore from a client older than the server fails, because that client always sends `targetNamespace`. Both belong in the edge cases and in the changelog fragment. The other findings are small: a test gap for the environment restore's target instance, a stale repository docstring, a unit-test fixture that needs an active instance, and a question about the security side of the bug.

Facts checked in the code for this report:

- `Restore.target_instance_id` is a foreign key to `applicationinstance.id`. Application instances are hard-deleted only by `delete_for_environment` in [`repository/deployment.py`](../../../backend/styrmin_backend/repository/deployment.py), which sets `target_instance_id` to null on the rows that point to them first. So recording the active instance on every in-place restore cannot block a deletion.
- The agent chart's ClusterRole grants `get`, `create`, `delete` and `list` on `namespaces` in every namespace ([`helm/agent/templates/roles.yaml`](../../../helm/agent/templates/roles.yaml)). Which service account the restore Job runs as was not checked.
- The in-place unit-test fixture `make_chain` in [`test_restore.py`](../../../backend/tests/unit/services/backup/test_restore.py) builds a deployment without an active instance; `make_counterpart` shows how to set one (`set_active_instance`).
