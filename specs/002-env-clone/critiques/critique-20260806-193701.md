# Critique Report: Environment Clone

**Feature**: `specs/002-env-clone` | **Date**: 2026-08-06 | **Artifacts reviewed**: spec.md, plan.md, research.md, data-model.md, contracts/graphql.md, quickstart.md, constitution v1.4.1

## Executive Summary

The spec is unusually well-grounded (seeded from a grilled, user-confirmed brief; zero clarification markers) and the plan composes almost entirely on shipped, tested machinery (ADR-0055 records, `deploy_application`, the Velero pipeline). The one genuinely novel mechanism — data-only cross-target restore through a scratch namespace — is the right architecture (the three identity blockers it dissolves are real and verified in code), but the plan as written under-specifies two operational hazards of that mechanism: the scratch namespace transiently runs a live copy of the source application with source credentials and **no network restrictions** (E1 — ironically, the exact interference hazard that motivated this feature), and the saga has **no bounded waits** (E2 — a stuck counterpart pins the clone `IN_PROGRESS` forever with only the delete-record escape hatch). Both are cheaply fixable at design time. One architectural assumption was verified during this critique rather than left latent: INTERNAL Prefect flows have direct DB access (`workflows/templates/backup.py` docstring + `get_unit_of_work()` call sites), so the saga flow can legally call creation services — the plan should name the INTERNAL/USER flow split explicitly.

**Verdict: ⚠️ PROCEED WITH UPDATES** — two must-address items, both resolvable with bounded edits to research.md/plan.md/quickstart.md; no rethink required.

## Product Lens Findings

### 3a. Problem Validation — sound

Issue #6 + the grilled brief (comment 5208479529) establish the operator pain directly; scope carving (isolation → P2, cross-cluster → blocked by ADR-0039, point-in-time → out) is aggressive and correct.

### 3b. User Value Assessment

- **P1 (💡)**: Between counterpart `RUNNING` and data-restore completion, the cloned application is live with **empty/fresh data** (and briefly flips `RESTORING`). An operator watching the clone may mistake the empty app for a failed clone. Suggestion: document the hydration window in the docs task, and let the Clones tab's per-deployment results make the phase visible (`cloned` only after data lands).
- **P2 (💡)**: The frontend clone dialog pre-checks "eligible deployments", which requires `internal` and active-instance visibility on the `Deployment` GraphQL type for a client-side filter. Verify both fields are already exposed; if either is missing, the additive field needs its own propagation test (Constitution §V).

### 3c. Alternative Approaches — adequately covered

Research D2 enumerates and rejects the four plausible alternatives with code-anchored reasons; no simpler design reaches SC-004 (data fidelity) without hitting the resource-identity blockers.

### 3d. Edge Cases & UX — strong, one addition

Spec edge rulings are complete and the D4 concurrency amendment is honest and documented. Addition folded into E1 below (the scratch namespace is a *user-facing* trust issue, not just an engineering one).

### 3e. Success Measurement — sound

SC-001..005 are measurable, technology-agnostic, and each maps to a quickstart assertion.

## Engineering Lens Findings

### 4a. Architecture Soundness

- **E3 (💡, verified during critique)**: The plan has the saga flow calling `create_environment` / `deploy_application` / `create_restore` — legal **only** because INTERNAL flows (styrmin-work-pool) do DB operations directly (`workflows/templates/backup.py:1-11` docstring; `get_unit_of_work()` at :346 et al.), while USER flows are K8s-only. The plan should state the split explicitly: `EXECUTE_ENVIRONMENT_CLONE` and `EXECUTE_CLONE_RESTORE` are INTERNAL (DB + orchestration); the scratch Velero restore **and the exec-based transfer** are a USER flow (K8s ops only), mirroring `execute_velero_restore`'s split. Without this stated, an implementer could put exec work in the INTERNAL flow or DB work in the USER flow.

### 4b. Failure Mode Analysis

- **E2 (🎯)**: **Unbounded waits.** The saga waits on (a) backup terminal status, (b) each counterpart reaching `RUNNING`, (c) each data restore. None has a timeout in the plan. A counterpart stuck `Pending` on cluster capacity — explicitly anticipated by the spec ("doubled footprint") — pins the clone `IN_PROGRESS` forever; FR-008 then pins the backing backup undeletable until someone finds the delete-record escape hatch. Suggestion: explicit per-step timeouts (backup-wait, per-counterpart running-wait, per-constituent restore timeout mirroring `DEFAULT_RESTORE_TIMEOUT`), each timeout attributing that deployment `failed` with reason and **continuing** (per-deployment isolation, FR-011), `finished_at` stamped in a `finally`.
- **E4 (💡)**: A flow crash mid-constituent leaks a scratch namespace. Suggestion: label scratch namespaces (`styrmin.io/environment-clone-restore=<restore_id>`), delete in `finally`, have the E2E assert zero `styrmin-clone-*` namespaces post-run, and document manual cleanup for hard crashes.

### 4c. Security & Privacy Review

- **E1 (🎯, converges with Product)**: **The scratch namespace transiently runs the source application unrestricted.** FSB data restore requires restoring the pods, so the source app boots in the scratch namespace with the source's secrets and config — and since the backup's NetworkPolicies are excluded from the restore, it runs with **no network restrictions at all**. A clone of production could therefore briefly interfere with production systems (send mail, hit webhooks) from the scratch namespace — precisely the hazard the user named as the isolation motive. Suggestion: the USER flow creates the scratch namespace **and a deny-all-egress/ingress NetworkPolicy in it before invoking the Velero restore** (the backup's own policies are excluded, so deny-all stands unopposed; the FSB node-agent and API-server exec paths do not traverse the pod network, so data restore and file transfer are unaffected). Document the residual risk: NetworkPolicy enforcement is CNI-dependent (same caveat the P2 isolation slice already carries).

### 4d. Performance & Scalability

- **E5 (💡)**: Constituent restores run sequentially: N × (scratch restore + transfer). For tens of deployments this is hours, which the spec tolerates (no time bound) but the SDK's `wait_for_clone(max_wait=1800)` default does not. Suggestion: keep sequential in v1 (simplicity, bounded cluster load), document the default's assumption and the override, and note parallelism as future work in the ADR.

### 4e. Testing Strategy — strong, two additions

Derivation property tests, propagation tests, conformance tuple, dual-entrypoint E2E all planned. Add: unit tests for the deny-all-policy prelude (E1) and for timeout attribution (E2); E2E asserts scratch-namespace cleanup (E4, already implied by quickstart §3.6 — make it explicit).

### 4f. Operational Readiness

- **E6 (💡)**: 001 D1 established structured audit log lines (`env_backup_fanout_dispatched …`). The clone saga should emit the same family: `env_clone_started/env_clone_step/env_clone_finished` with outcome counters, so a stuck clone is diagnosable from server logs alone. Migration is reversible (data-model.md); rollback = discard-and-retry by design.

### 4g. Dependencies & Integration Risks — sound

`namespaceMapping` and `excludedResources` are native Velero Restore fields; the mapping path is already built and unit-tested in this codebase (dormant). The pvc-patch resource modifier applies unchanged to scratch restores. Agent RBAC for exec/helper pods is already flagged in the plan as an implementation check.

## Cross-Lens Insights

- **X1 (🎯 = E1)**: The scratch-namespace interference risk is simultaneously the feature's own product promise ("clone must not interfere") violated by its implementation detail. Deny-all-first is cheap and turns the scratch namespace into the *most* isolated part of the pipeline.
- **X2 (💡 = P1 + E5)**: The hydration window and sequential duration both shape operator expectations — one docs section ("What to expect while a clone runs") covers both.
