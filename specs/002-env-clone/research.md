# Research: Environment Clone

**Feature**: `specs/002-env-clone` | **Date**: 2026-08-06

All unknowns from the Technical Context are resolved below. Grounding: the shipped 001-env-backup-restore machinery (`services/backup/environment.py`, ADR-0055), the restore execution pipeline (`workflows/templates/backup.py`), and the creation services (`services/environments.py`, `services/deployment.py`).

## D1 — Clone orchestration is a new INTERNAL Prefect flow, not a service-layer fan-out

**Decision**: `cloneEnvironment` is a thin ADMIN mutation: validate synchronously (source environment exists, new name free in the cluster, selection ids all eligible — zero side effects on failure, FR-012), create the `EnvironmentClone` row, dispatch a new INTERNAL flow `EXECUTE_ENVIRONMENT_CLONE`, return the record (`PENDING`). The flow orchestrates the saga by calling existing service functions: (1) create the environment backup (selection-scoped, D4) and **wait** for its derived status to become terminal; (2) create the new environment from captured config + operator override, copy the BSL assignment, recompute capabilities; (3) per snapshot entry: create the counterpart deployment (D3), wait for it to reach `RUNNING`, then run the cross-target data restore (D2); (4) record attribution events throughout and stamp `finished_at` on exit.

**Bounded waits (critique E2)**: every wait has an explicit timeout — backup-terminal wait, per-counterpart `RUNNING` wait (a counterpart stuck `Pending` on cluster capacity is an anticipated case), and a per-constituent restore timeout mirroring `DEFAULT_RESTORE_TIMEOUT`. A timeout attributes that deployment `failed` with reason and the saga **continues** (per-deployment isolation, FR-011); `finished_at` is stamped in a `finally` so a survivable failure can never pin the clone — and thereby the FR-008 backup guard — in `IN_PROGRESS`. The saga also emits structured audit log lines (`env_clone_started` / `env_clone_step` / `env_clone_finished` with outcome counters), parity with `env_backup_fanout_dispatched` (critique E6).

**Rationale**: 001's D1 kept fan-out in the service layer because every constituent was fire-and-forget with no ordering. Clone is different in kind: it has **ordered waits** (backup terminal before anything materialises — FR-002; deployment `RUNNING` before data restore) that a synchronous service function cannot perform. A Prefect flow is the platform's one sanctioned place for long-running orchestration (Constitution §III: "async workflows go through Prefect orchestration"). Business rules stay in services — the flow only sequences service calls, mirroring how `execute_restore_workflow` already drives `update_restore_status`.

**Alternatives considered**: (a) Service-layer fan-out à la 001 — impossible: cannot wait for backup completion inside a request. (b) Client-side orchestration (CLI/SDK drives the steps) — rejected: violates SC-001 (single operation on every surface), makes attribution unownable, and GraphQL clients would each reimplement the saga. (c) Chained flows with callbacks — rejected: more moving parts than one flow with explicit steps, and Task-callback plumbing (ADR-0019) adds nothing here.

## D2 — Cross-target constituent restore is **data-only**, via a scratch-namespace Velero restore + in-cluster transfer

**Decision**: A constituent backup is restored into a counterpart deployment in four phases. Orchestration and DB work live in a new INTERNAL flow `EXECUTE_CLONE_RESTORE` (one per constituent, dispatched sequentially by `EXECUTE_ENVIRONMENT_CLONE`); the Kubernetes-side work (phases 1–3) runs as a USER flow, mirroring `execute_velero_restore`'s INTERNAL/USER split — INTERNAL flows have direct DB access via `get_unit_of_work()`, USER flows are K8s-only (`workflows/templates/backup.py:1-11`, verified during critique E3):

0. **Isolation prelude (critique E1)**: create the scratch namespace `styrmin-clone-<restore_id>` — labelled `styrmin.io/environment-clone-restore=<restore_id>` — and apply a **deny-all ingress+egress NetworkPolicy** in it *before* invoking the Velero restore. The backup's own NetworkPolicies are excluded from the restore (below), so deny-all stands unopposed. The FSB node-agent and API-server exec paths do not traverse the pod network, so data restore and file transfer are unaffected. This closes the transient-interference window in which the source app boots in the scratch namespace with source credentials; residual risk (NetworkPolicy enforcement is CNI-dependent) is documented — the same caveat the P2 isolation slice carries.
1. **Scratch restore**: Velero-restore the constituent backup into the scratch namespace using `namespaceMapping {styrmin-<source_deployment_id>: <scratch_ns>}` — the mapping support already exists and renders correctly (`build_velero_restore`, `agent/service/kubernetes/resources/builders/backup.py:41-71`; currently dead code, unit-tested). The restore **excludes platform-identity resources** (`styrmindeployments`, Flux `helmreleases`, `networkpolicies`, ingress/middleware kinds): the scratch namespace receives the app's workloads, PVCs, secrets, and configmaps under their internally-consistent source names, unmanaged by the operator or Flux. File-system backup populates PVC data through the restored pods' Velero init containers, so data lands even if app containers crash-loop in the scratch namespace.
2. **Transfer**: move data from scratch to the counterpart's namespace. Per strategy kind (registry `services/backup/service.py:40-47`):
   - **postgres / mariadb / mongodb / neo4j**: stream the dump file(s) from the scratch backup volume into the counterpart pod's backup mount (exec-based tar streaming, the `kubectl cp` mechanism), then exec the strategy's existing restore command in the counterpart's component pod — the same commands `get_restore_hooks` builds today (`velero/hooks.py`), factored into shared command builders so hook path and clone path cannot drift. Counterpart pods are `RUNNING` and target-labelled (`styrmin/component` labels are not deployment-scoped), so the exec targeting works unchanged.
   - **disk**: stop the counterpart component (existing component lifecycle controls), quiesce the scratch workload, copy PVC contents scratch→target via short-lived helper pods + tar streaming, restart the component.
   - **action**: attributed as failed/skipped with reason "driver action restore is not implemented" — **parity with in-place restore, which also has no action-restore path today** (nothing anywhere invokes driver actions on the restore side).
3. **Teardown**: delete the scratch namespace unconditionally (`finally`), delete the scratch-restore Velero object per existing TTL conventions. A hard flow crash can still leak a scratch namespace — the label from phase 0 makes leaked namespaces identifiable, the E2E asserts zero `styrmin-clone-*` namespaces post-run, and the docs describe manual cleanup (critique E4).

**Outcome semantics for strategy-less constituents (critique Q1)**: a deployment whose components declare no restorable data strategy (e.g. `action`-only, which has no restore path even in place) completes with outcome `cloned` and a reason note ("no restorable data strategies") — vacuous data success, parity with in-place restore. Phases 0–3 are skipped entirely for such constituents.

The constituent `Restore` row reuses the existing dormant cross-target fields: `target_instance_id` (already plumbed through GraphQL/SDK/CLI but never read — `services/backup/service.py:417`) plus a new nullable `environment_clone_id` FK. `create_restore` is extended to resolve **two** deployments (source from the backup, target from `target_instance_id`) and to apply the `internal` check, `RESTORING` flip, and completion status to the **target** — today all of these silently hit the source (`service.py:371-428`).

**Rationale**: The naive alternative — full Velero restore into the counterpart's namespace — is structurally broken, not merely risky: (a) every chart-rendered resource name embeds the source deployment UUID (`release_reference = namespace = styrmin-<deployment_id>`, `services/context.py:129-130`), and Velero's `namespaceMapping` never renames resources, so restored `data-styrmin-<SOURCE>-0` PVCs can't bind to the target's StatefulSets; (b) the in-place USER flow **deletes the target namespace first** (`workflows/templates/backup.py:212-246`), which would destroy the counterpart just deployed; (c) the restored `StyrminDeployment` CRD and `styrmin/deployment_id` labels carry the source's identity, so the operator and status reporter would mis-attribute the target namespace to the source deployment. Data-only restore dissolves all three: the counterpart owns every platform-managed resource through its own ordinary reconciliation, and only application data crosses namespaces. The `Backup.component_statuses` column already carries the full per-component strategy config (kind, container, backup_mount_path, backup_volume), so the transfer plan is reconstructable from the backup row alone — consistent with FR-007 (never re-read the live source).

**Alternatives considered**: (a) Full restore + post-restore identity rewrite — rejected: renaming a Helm release in place is not a thing; Flux would install a second, target-named release beside the restored one (duplicate workloads, ambiguous component labels). (b) Velero resource modifiers to rename PVCs on the way in — rejected: modifiers patch fields, but Velero does not support renaming restored resources (PV rename only), and under file-system backup the PodVolumeRestore linkage matches pod volumes by name, which a rename breaks. (c) Per-constituent in-place pipeline with parameterised names — rejected: inherits (b) plus the namespace-deletion pre-step. (d) Restore only PVC objects into the target namespace (no scratch pods) — rejected: under file-system backup, PVC data is populated by the restored *pods'* init containers; a bare PVC restore arrives empty.

**Known accepted risks** (documented, mirrored from in-place restore where they already exist): dump-replay strategies inherit the target's DB name/user env — identical here by construction since counterpart config is the captured source config; the existing `role "simple-app" does not exist`-class FIXME (`hooks.py:261-264`) applies equally. Agent RBAC must cover pod exec + helper-pod creation in `styrmin-*` namespaces — verify against the agent's ClusterRole during implementation and extend the chart if missing (requests only, no limits — Helm guideline).

## D3 — Counterpart deployments through `deploy_application`, driver version re-resolved by fingerprint

**Decision**: Each counterpart is created with the existing `deploy_application` (`services/deployment.py:1071`), passing the snapshot's `deployment_name`, `config`, `parameters`, `application_version`, and a **pinned `driver_version_id`** resolved from the snapshot: first `get_by_identity(driver_name, driver_version, driver_fingerprint)` (exact content match, ADR-0053), falling back to `get_by_driver_and_version`, with a recorded attribution note when the fallback fired (same version string, different fingerprint). A snapshot whose driver identity was degraded at capture (`driver_name == ""`) or whose driver version no longer resolves → that deployment is attributed failed; the clone proceeds (`PARTIAL`, spec edge case 2). `created_by_user_id` is threaded from the mutation caller through the flow parameters.

**Rationale**: `deploy_application` already does everything the clone needs — per-environment tombstone-aware name uniqueness (captured names transfer collision-free into a fresh environment, ADR-0011), driver-version pinning with typed errors, parameter validation, service creation, and `apply_state` dispatch (Constitution §I/§II: counterparts are ordinary deployments reconciled the ordinary way). The snapshot stores driver identity as name+version+fingerprint, not a row id (ADR-0055 data model), so re-resolution is required by construction; preferring the fingerprint honours the provenance guarantee.

**Known v1 limitation (documented)**: `DeploymentSnapshot` does not capture `service_name_overrides`, so cloned deployments get driver-default service names. Service FQDNs are computed at runtime (ADR-0022) and are clone-appropriate regardless. Recorded in docs; extending the snapshot is future work for the backup feature, not this one.

## D4 — Backup step: extend `create_environment_backup` with an optional selection; define "backup succeeded"

**Decision**: `create_environment_backup` gains an optional `deployment_ids: list[UUID] | None` filter applied on top of the existing eligibility rule; `None` keeps today's behaviour (all eligible — FR-003 default). The clone mutation validates upfront that every selected id is an eligible deployment of the source environment (`VALIDATION_ERROR` otherwise). The clone flow polls the backup's derived status to terminal: **`FAILED` → clone `FAILED`, nothing materialises (FR-002, acceptance 5); `COMPLETED` or `PARTIAL` → proceed**, with each failed constituent already attributed by the backup's own `constituent_errors` and carried into the clone's attribution (spec FR-011 best-effort).

**Rationale**: Selection at backup time (not clone-assembly time) is what the spec's US2 acceptance 1 demands ("only the selected deployments are backed up") — it also avoids paying backup cost for excluded deployments. `PARTIAL` proceeding matches the environment-restore philosophy ("restore what's usable, report what isn't"): a 19/20 backup should still produce a 19-deployment clone with one attributed failure, not zero clones.

**Spec amendment (concurrency, edge case 4)**: the shipped one-environment-level-operation guard (`_guard_no_environment_operation_in_progress`, ADR-0055/D6) rejects a second environment backup while one is in flight. Two concurrent clones of one source therefore collide at the backup step. Rather than weaken a shipped safety guard, the spec's edge ruling is amended: **a second concurrent clone of the same source fails fast with the existing typed `ALREADY_IN_PROGRESS` error and zero side effects** (the name reservation happens at validation time, nothing has materialised). Clone-of-clone and clones of *different* sources remain unrestricted. Recorded in the alignment check as a deliberate deviation from the brief.

## D5 — `EnvironmentClone` record: inputs + attribution events stored; status derived on read, never stored

**Decision**: One new table `environmentclone`: `source_environment_id` (nullable FK, `ON DELETE SET NULL` — source deletion mid- or post-clone never touches the record), `source_environment_name` (copied string, survives source deletion), `environment_backup_id` (nullable FK — survives later backup deletion), `created_environment_id` (nullable FK, `SET NULL` on clone-environment deletion), `new_environment_name`, `selected_deployment_ids` JSON, `environment_config_override` JSON, `deployment_results` JSON (attribution events: one entry per selected snapshot — `{deployment_id, deployment_name, counterpart_deployment_id?, outcome: cloned|skipped|failed, reason?}`), `finished_at` (timestamp event, set once by the flow on exit), `created_by_user_id`. Plus one new nullable FK `restore.environment_clone_id`. Status is a pure derivation: `finished_at` unset → `PENDING`/`IN_PROGRESS` (refined by backing-backup status and linked restores); `finished_at` set → `COMPLETED`/`PARTIAL`/`FAILED` computed from `deployment_results` + linked constituent `Restore` rows, tolerating later row deletion the same way ADR-0055 tolerates deleted constituents (visible gap, count identity against `deployment_results`).

**Rationale**: FR-009 mandates the ADR-0055 derived-status principle; the clone's extra wrinkle is that constituents appear *progressively* (the saga creates them step by step), so the terminal/non-terminal pivot needs one recorded **event** (`finished_at`) rather than a stored status — an event cannot contradict child state, it only says "the saga stopped appending". Every FK is nullable-by-design so the record survives deletion of everything it references (spec: clone record is history; SC-005 discard-and-retry must not be blocked by bookkeeping).

**Escape hatch**: `deleteEnvironmentClone` is legal **regardless of derived status** (mirrors ADR-0055's rule for environment backups). This matters doubly here: the FR-008 backup-deletion guard keys off "an in-flight clone depends on it", so a crashed flow pinning a clone `IN_PROGRESS` forever would otherwise pin the backup undeletable forever. Deleting the clone record releases the guard; deleting the clone *environment* is ordinary `deleteEnvironment` (FR-013) and never touches the record.

## D6 — Guards and typed errors

**Decision**: New `ServiceError` subclasses, existing error codes only: `EnvironmentCloneNotFoundError` (`NOT_FOUND`), `EnvironmentCloneSelectionError` (`VALIDATION_ERROR`, names the offending ids), `EnvironmentBackupInUseError` (`OPERATION_DENIED`) raised by `delete_environment_backup` when a linked clone is non-terminal (FR-008; also raised through the `delete_environment_backups_for_environment` cascade so `deleteEnvironment` on the **source** reports it cleanly). Name validation reuses `EnvironmentAlreadyExistsError` upfront (FR-012); a TOCTOU loss at creation time inside the flow becomes a `deployment_results`-level terminal failure with reason (clone `FAILED`, backup retained). Concurrency: D4's `ALREADY_IN_PROGRESS` reuse.

**Rationale**: Constitution §IV typed errors; every code already exists in `ErrorCode`, so no new error-code surface. Refusal (not cascade-failure) on backup deletion was the spec's chosen semantics — one EXISTS-style check over the clone's non-terminal state, same derivation philosophy as ADR-0055's guard.

## D7 — GraphQL surface and authorization

**Decision**: Mutation `cloneEnvironment(environmentId: UUID!, newEnvironmentName: String!, deploymentIds: [UUID!] = null, environmentConfigOverride: JSON = null) -> EnvironmentClone` — **ADMIN**. Mutation `deleteEnvironmentClone(environmentCloneId: UUID!) -> Boolean` — READ_WRITE (record-only deletion, same class as `deleteEnvironmentBackup`). Queries `environmentClone(environmentCloneId)` and `environmentClones(environmentId)` (source-scoped, newest first) — authenticated reads, ungated like the environment-backup queries. Full contract in `contracts/graphql.md`.

**Rationale**: ADMIN follows the `restoreEnvironmentBackup` precedent verbatim (`mutation.py:966-971`): clone writes an `Environment.config` the caller did not author (captured + override), triggers backups, and runs restores — a strict superset of restore's privilege footprint (spec FR-014, grilled and confirmed). The config-override merge is **top-level shallow** (`{**captured, **override}`), validated by the existing `validate_environment_config` before the environment is created; no key-removal semantics in v1 (documented in the contract).

## D8 — SDK and CLI shapes

**Decision**: SDK facade `client.environment_clones` (ADR-0037 shape): `create(environment_id, new_environment_name, deployment_ids=None, environment_config_override=None)`, `get(environment_clone_id)`, `list(environment_id)`, `delete(environment_clone_id)`, `wait_for_clone(environment_clone_id, max_wait=1800, interval=10)` (terminal = `COMPLETED`/`PARTIAL`/`FAILED`, returns last observation on timeout — same contract as the env-backup pollers). CLI: new Cyclopts sub-app `env-clones` with `create` (positional source environment, dual-identifier resolution per ADR-0031, `--new-name` required, repeatable `--deployment`, `--config-override` JSON string, `--wait/--max-wait/--interval`), `get`, `list`, `delete` — mirroring `environment_backups.py` including the structural-Protocol renderers and the synchronous-terminal-failure reporting rule.

**Rationale**: One-namespace-per-resource CLI layout (`env-backups` precedent); the longer default `max_wait` reflects that a clone waits on a full backup plus N deployment boots plus N **sequential** data restores — the docs state this assumption and the override, and the ADR notes constituent-level parallelism as future work (critique E5).

## D9 — Frontend surface

**Decision**: (1) A `CloneEnvironmentDialog` launched from a "Clone" action on the environment list row and on the environment detail page — fields: new environment name, deployment multi-select (pre-checked eligible deployments of the source), optional config-override JSON editor; gated `IfRole minimum="ADMIN"`. (2) A "Clones" tab on the environment detail page (source-side), listing clone records with derived status, per-deployment attribution expansion, and a link to the created environment — structured like `EnvironmentBackupsTab` (10 s auto-refresh, TanStack Query invalidation of `["ListEnvironmentClones"]` + `["ListEnvironments"]`).

**Rationale**: `CreateEnvironmentDialog` + `EnvironmentBackupsTab` are the two established patterns; clone composes them. The clone appears in the environments list as an ordinary environment the moment it is created — no special rendering (spec: clone is ordinary).

**Implementation check (critique P2)**: the dialog's eligibility pre-filter needs `internal` and active-instance visibility on the `Deployment` GraphQL type — verify both are exposed; an additive field carries its own propagation test (Constitution §V). The docs gain a "What to expect while a clone runs" section covering the hydration window (counterpart live with empty data until its restore completes, visible per-deployment on the Clones tab) and the sequential-duration expectation (critique P1/X2).

## D10 — E2E strategy: extend the `shard_backup` scenario, dual-entrypoint

**Decision**: One new dual-entrypoint `@pytest.mark.ci` node `test_environment_clone_lifecycle` in `backend/tests/e2e/test_backup_restore.py` (module already carries `shard_backup`), reusing the same booted stack (`deployed_simple_app` + the second deployment the env-backup test already creates). Scenario: write a data marker → clone with a selection excluding one deployment → wait terminal → assert the clone environment exists with only the selected counterpart, marker data present (SC-004), source config + declared state unchanged (SC-002), full attribution on the record (SC-003) → delete the clone environment → re-clone under the same name succeeds (SC-005) → cleanup. New `ScenarioDriver` methods `clone_environment`, `get_environment_clone`, `wait_for_environment_clone`, `delete_environment_clone` (+ page objects for the dialog and Clones tab), added to the explicit tuple in `backend/tests/unit/test_e2e_driver_conformance.py`.

**Rationale**: Constitution §V reuse-before-boot — the backup shard already runs Velero + MinIO + the app stack this needs; the feature ships a UI flow, so dual-entrypoint is mandatory. Local PASS evidence recorded per §V for both entrypoints.
