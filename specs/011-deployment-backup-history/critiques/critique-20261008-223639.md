# Critique Report: Keep a Deployment's Backup History When It Gets a New Instance

**Date**: 2026-10-08
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ✅ PROCEED

## Executive Summary

The spec and the plan solve the problem in issue #304 with the smallest change that covers every place an operator lists backups: a join through the existing instance-to-deployment link, one optional GraphQL argument that follows ADR-031, and a version column on the Backups tab and in the CLI. Nothing in the design changes the database, restores or access rules, and `backups(instanceId:)` keeps its results. Each finding below was checked against the code on this branch. No finding blocks task generation. Four recommendations are clear and low risk, and were applied to `spec.md`, `plan.md`, `research.md` and the contracts after this report:

- P3: label the new Backups tab column "Application version"
- P4: say what `restore --last --target-instance-id` lists
- P5: say how the CLI reaches a deleted deployment's history
- E5: keep the two `finally` reverts in the E2E test independent

Two questions are left for the person who reviews the fix. Both concern follow-up work that the PRD already places out of scope.
