This is the changelog for Styrmin.
All notable changes to this project will be documented in this file.

## [Styrmin - v0.1.48](https://github.com/opsmill/styrmin/tree/v0.1.48) - 2026-10-15

### Removed

- Removed the Redeploy button from the deployment page. Clicking it did nothing. ([#428](https://github.com/opsmill/styrmin/issues/428))
- Removed the `component_command` and `component_args` driver template filters. Loading a driver version whose `values.j2.yml` calls either one, or the earlier retired `component_env_vars`, now fails with `RETIRED_TEMPLATE_FILTER` and an error that names the line and the [migration guide](https://styrmin.pages.dev/docs/drivers/migrating-container-overrides). A driver version loaded earlier that still calls them fails rendering with the same error, also when no override is set, so a deployment pinned to it fails on its next change until it moves to a migrated driver version; its pods keep running meanwhile. Removed `spec.container_overrides` from the driver specification file (a `driver.styrmin.yml` that still contains it fails to load with an error that links the migration guide), from the stored driver version (a database migration drops the column) and from the API and SDK: `ApplicationDriverVersion.containerOverrides`, the `DriverContainerOverrideDoc` type, the SDK's `get_driver_container_override_docs` method and the `DRIVER_CONTAINER_OVERRIDE_DOC_COMPONENT_MISMATCH` error code. Before you upgrade Styrmin, list the stored `command` and `args` overrides of your deployments with `styrminctl deployments get` and remove the values you do not want with `styrminctl deployments update --config` or `styrminctl deployments apply`; the Configuration editor of earlier releases cannot submit a change that only removes them. After the upgrade, Styrmin applies them to every component with a component container on the next render of the deployment, which an env var edit on its environment or a cluster config update can also start, so values that a driver template did not pass to the chart reach the pods for the first time: `command` on the infrahub `server`, for example, and every value on a driver whose template never called the filters, such as `slurpit`, `semaphore`, `infrahub-mcp` and `db-test`. See [Before you upgrade Styrmin](https://styrmin.pages.dev/docs/drivers/migrating-container-overrides#before-you-upgrade-styrmin). ([#457](https://github.com/opsmill/styrmin/issues/457))

### Added

- Added steps and failure causes to tasks, backups and restores. Each task on the deployment page lists its steps in order (planning the changes, each hook mode that runs, writing the StyrminDeployment resource, and the operator phases from network policies and secrets to the wait for readiness) with status, duration, attempts and the error of each failed attempt; the HelmRelease step shows FluxCD's current reason, FluxCD rollbacks and the pods that are not ready, and a failed command run by an action or by `runJob` keeps the end of its output (the last 200 lines, at most 64 KiB), which every signed-in user can read, so action commands must not print secrets. Each task shows a result calculated from its steps and from the tasks its hook started (`RUNNING`, `FAILED`, `SUCCEEDED`, or `SUPERSEDED` with a link to the task that interrupted it), the page refreshes every 10 seconds and says when the agent has sent no report for more than 60 seconds, restores show their three steps and backups one step per component. Available as `Task.steps`, `Task.result`, `Task.startedBy`, `Task.startedTasks`, `Backup.steps`, `Restore.steps` and `Query.step` in the API; `tasks.step_output()`, `tasks.failed_step()` and the `FailedStep`, `TaskStep`, `StepOutput`, `StepStatus`, `StepKind` and `TaskResult` models in the SDK; a result column, a steps table and a started-tasks table in `styrminctl tasks get`; and the failed step's name and error in the `failed` line of `styrminctl deployments apply --wait`. The agent's role can now read Velero `PodVolumeBackup` objects. Tasks, backups and restores from before this release show no steps. ([#2](https://github.com/opsmill/styrmin/issues/2))
- Added the logo, description and links of each driver to the driver pages. A driver author sets them in `spec.info.icon`, `spec.info.description` and `spec.info.links` of `driver.styrmin.yml`. The driver list page shows the logo of each driver and the first line of its description, and the driver detail page shows the logo, the first three lines of the description and the links of the selected driver version; a "Show more" button shows the rest of a longer description, the driver list filter matches descriptions, and each link shows the host it goes to and opens in a new browser tab. The browser of each person who views the page loads the logo from its URL. The pages show the logo on a white tile, and show the generic package icon until the logo has loaded and when a driver version has no logo or the browser cannot load it. To stop the browser requests to logo hosts, set the Helm value `styrmin.driver.showLogos` (environment variable `STYRMIN_DRIVER_SHOW_LOGOS`) to `false`; the API then returns no logo URL. A driver version loaded before this release gets its logo, description and links when the same driver is loaded again. Available as `icon`, `description` and `links` on `ApplicationDriverVersion` in the API. ([#272](https://github.com/opsmill/styrmin/issues/272))
- Added an anonymous daily telemetry report from the Styrmin server, on by default: once a day at 02:43 UTC the task worker sends the install ID, the Styrmin, Python and operating system versions, the number of clusters, environments and deployments, and each loaded application driver version with its name as written and the number of deployments that use it. Turn it off with the Helm value `styrmin.telemetry.enabled: false`, `STYRMIN_TELEMETRY_ENABLED=false`, `DO_NOT_TRACK=1` or `STYRMIN_TELEMETRY=0`, and view the exact report data, without sending it, with `styrmin telemetry show` in the server pod; see [Telemetry & privacy](https://styrmin.pages.dev/docs/reference/telemetry#server-telemetry). ([#274](https://github.com/opsmill/styrmin/issues/274))
- Added the application version of each backup to a deployment's backup history: an "Application version" column on the Backups tab, an `application_version` column in `styrminctl backups list`, an "Application version" line in `styrminctl backups get`, and `instance.applicationVersion` in the API and SDK. The Backups tab marks the backups of the current instance, shows the time each backup was created, marks a backup whose expiry date has passed as "Expired", and shows an error with a "Try again" action when the list cannot be loaded. API users can list a deployment's backup history with `backups(deploymentId:)`, and SDK users with `list_backups(deployment_id=...)`. ([#304](https://github.com/opsmill/styrmin/issues/304))
- Added an `input` argument to the `updateDeploymentVersion` GraphQL mutation, with the fields of `updateDeployment`: the config, name, parameters and service name overrides it carries are checked against the target driver version and application version and written with the version in one task. It is also available as `input` on the SDK's `deployments.update_version()` and as `--config` on `styrminctl deployments update-version`, both of which need a server with this release. `styrminctl deployments apply` now warns on stderr about env vars and image overrides that it stores but that the driver version cannot apply, and the SDK returns them as `ApplyOutcome.inapplicable_components`, next to the new `ApplyOutcome.error_code`. ([#388](https://github.com/opsmill/styrmin/issues/388))
- Added `styrminctl clusters update`, `clusters.update()` in the SDK, the `updateCluster` GraphQL mutation and an Edit button on the cluster detail page, which administrators use to change a cluster's config without recreating the cluster, its environments and its deployments. Styrmin saves the whole new config and redeploys each deployment whose resolved config changes; the result lists the deployments that are redeployed, that wait for a dedicated ingress controller and that could not start, and `--dry-run` (`dryRun`) and the edit dialog's review step list them before anything is saved. `styrminctl clusters get --json` prints the config to edit. ([#423](https://github.com/opsmill/styrmin/issues/423))
- Added `drivers.list()` to the Python SDK, which returns every application driver with its versions.
- Added the bundled generic-app driver, which deploys any single-container HTTP application (for example a Streamlit app, or Semaphore with SQLite) with its image, environment variables, command and optional volume set per deployment.
- Added two operator settings for rollouts: `STYRMIN_OPERATOR_HELM_RELEASE_TIMEOUT` sets how many seconds FluxCD gets for each install or upgrade before it rolls the release back (300 by default, the previous fixed 5 minutes), and `STYRMIN_OPERATOR_RETRY_DELAY` sets how many seconds the operator waits before it retries a rollout step that failed with a temporary error (30 by default, the previous fixed value). Keep `STYRMIN_OPERATOR_DEPLOYMENT_READY_TIMEOUT` below the HelmRelease timeout so that a failed rollout still lists the pods that are not ready.

### Changed

- Changed the operator's default readiness timeout (`STYRMIN_OPERATOR_DEPLOYMENT_READY_TIMEOUT`) from 300 to 270 seconds, below FluxCD's 5-minute HelmRelease timeout, so a rollout that fails because its pods cannot start (for example `ImagePullBackOff`) lists those pods and their reasons before FluxCD's rollback removes them. A rollout that becomes ready between 270 seconds and 5 minutes now shows `FAILED`, then `RUNNING`. ([#2](https://github.com/opsmill/styrmin/issues/2))
- Changed the type of the tasks that a reconcile runs from `noop` (shown as "No-op") to the operation they start: `create_instance`, `update_instance`, `upgrade_instance`, `stop_components` or `start_components`; tasks recorded before keep `noop`, and `delete_deployment` tasks are now shown as "Delete". Changed `runJob` tasks to run through an internal `run_job` flow, which creates an action token for the `styrmin-actions` user and runs the job's command in a new user flow, `run_job_command`, so each `runJob` task now has two flow runs in Prefect and creates one `styrmin-actions` session while it runs; backups and restores also create one such session each. ([#2](https://github.com/opsmill/styrmin/issues/2))
- Changed the built-in `styrmin-actions` user so that no one can log in as it: `login` rejects its username whatever the password, `resetUserPassword` and `changePassword` refuse it with `FORBIDDEN`, and `createUser` refuses the username `styrmin-actions` with `FORBIDDEN`. Before, an admin could reset its password and then log in as it. ([#2](https://github.com/opsmill/styrmin/issues/2))
- Changed `styrminctl deployments apply --wait` and the SDK's `deployments.apply(wait=True)` and `apply_files(wait=True)` to wait up to 600 seconds instead of 300, so a deployment whose release fails can report the failed step instead of `wait timeout`. The wait still ends with `wait timeout` when the limit expires before a step fails, for example when the hooks of a deployment take longer than about 5 minutes. Added `--max-wait` to `deployments apply` and `max_wait` to the SDK methods to set another limit. ([#2](https://github.com/opsmill/styrmin/issues/2))
- Changed `styrmin config show` to list the kubeconfig path from `KUBECONFIG` as `kubeconfig` under `[kubernetes]`, now that the agent reads it with the other Kubernetes settings. The API token in `STYRMIN_TOKEN` is not shown. ([#95](https://github.com/opsmill/styrmin/issues/95))
- Changed `Environment.deployments` in the GraphQL API to leave out internal deployments, such as the ingress controller of a dedicated ingress, unless you pass `includeInternal: true`. `Deployment.internal` now returns `true` for these deployments when you request them. The Python SDK `deployments.list()` method takes a matching `include_internal` argument. ([#253](https://github.com/opsmill/styrmin/issues/253))
- Changed driver loading to report the `spec.info` values that it does not store. When `spec.info.icon` is not an absolute `https` URL, or a `spec.info.links` entry does not have exactly a `link` label and an absolute `http` or `https` `url`, the load still succeeds, leaves that value out and returns a warning that names the field; neither URL can contain a username or password. The GraphQL load mutations return the warnings in the new `loadWarnings` field, `styrminctl drivers load-version` and `styrminctl drivers load-local-version` print them, and the Load driver drawer shows them in a notification. Driver files with a placeholder such as `icon: xxxx`, which the earlier `DRIVERS.md` and the Infrahub example drivers contained, still load; replace the placeholder with a logo URL, or remove the line, to stop the warning. A driver load that fails for another reason now lists one line per invalid field instead of the raw validation output. ([#272](https://github.com/opsmill/styrmin/issues/272))
- Changed `styrminctl backups restore --last` to choose the newest completed backup from every instance of the deployment, not only from its active instance, and to skip backups whose expiry date has passed. When the chosen backup was taken of an earlier instance, the command now shows the backup's application version and the deployment's current one and asks for confirmation; `--yes` skips the question, and without a terminal the command refuses unless `--yes` is passed. The Restore dialog shows the same two versions and a warning. A restore into a deleted deployment is now refused with `OPERATION_DENIED`. The `instanceId` argument of the `backups` query is now optional; passing both `deploymentId` and `instanceId`, or neither, returns `VALIDATION_ERROR`, and the SDK raises `ValueError` before sending the request. ([#304](https://github.com/opsmill/styrmin/issues/304))
- Changed the SDK query that lists backups, which `styrminctl backups list` and `styrminctl backups restore --last` use, to take a `deploymentId` argument. A server from an earlier release rejects that query, so use a `styrminctl` and an SDK from the same release as the server. ([#304](https://github.com/opsmill/styrmin/issues/304))
- Changed `updateDeploymentVersion`, which the upgrade dialog, `styrminctl deployments update-version` and driver actions use, to recreate a deployment's services before it generates the new instance, and only when the driver version or a service name changes: a values template that reads `services` now gets the target driver version's services in the upgrade itself instead of one reconcile later. A call that keeps both the application version and the driver version now shows as an update in the deployment timeline instead of an upgrade. `styrminctl deployments apply` now rejects component config on a component that the target driver version does not declare even when the config is unchanged, so remove that config from the manifest in the same change that moves `spec.version`. The SDK's `deployments.apply()` now returns a `failed` outcome instead of raising when the server rejects the manifest. The errors for component overrides on an unknown component or a component without a component container now name the driver, driver version and application version that were checked. ([#388](https://github.com/opsmill/styrmin/issues/388))
- Changed `styrminctl clusters get` and `clusters list` to print the cluster config as JSON instead of Python dict text. ([#423](https://github.com/opsmill/styrmin/issues/423))
- Changed the environment update so that, when it turns the environment's own `dedicated_ingress` off and the cluster does not set `dedicated_ingress`, Styrmin removes the environment's dedicated ingress controller once the applications have been redeployed to the cluster's `ingress_class`. Before, the controller stayed until the last application in the environment was deleted. Also, when an environment's ingress controller reaches `RUNNING`, Styrmin now redeploys the applications of that environment that are not at the config they resolve to. ([#423](https://github.com/opsmill/styrmin/issues/423))
- Made listing a deployment's backups and each backup's restores faster on databases that hold many backups, for the Backups tab, `styrminctl backups list` and `styrminctl backups restore --last`: the database now indexes the columns these lists filter on, so it no longer reads every backup and restore row. `styrmin db migrate` creates the two indexes. ([#427](https://github.com/opsmill/styrmin/issues/427))
- Changed the FluxCD controllers that the agent chart installs from helm-controller v1.1.0 and source-controller v1.4.0 to helm-controller v1.6.5 and source-controller v1.9.6 (Flux v2.9.6), which support Kubernetes 1.34.1 and later; helm-controller keeps Helm v3's apply and health checks. Before each install and upgrade, a hook Job of the agent chart now applies the agent's CRDs (`styrmin-agent.crdUpgrade.enabled`), because Helm never updates them: on an existing installation it recreates the unused `OCIRepository` CRD, and fails the upgrade if the cluster has `OCIRepository` objects. ([#433](https://github.com/opsmill/styrmin/issues/433))
- Made starting an environment backup, an environment restore or an environment clone faster on databases that hold many backups and restores: the check that refuses to start one while an environment backup or restore is in progress no longer reads every backup and restore row, and neither does listing an environment's backups and their restores. `styrmin db migrate` creates the four indexes these queries read through. ([#455](https://github.com/opsmill/styrmin/issues/455))
- Changed how container `command` and `args` overrides reach pods: Styrmin now applies them after the Helm chart renders, to the component container the driver declares (`components.<name>.container`), together with env vars and image overrides, so a driver no longer passes them to the chart in `values.j2.yml`. An override replaces the whole `command` or `args` list, a field without an override keeps the value the chart renders, clearing an override brings back the chart's `command` and `args`, and overrides no longer reach chart Jobs, init containers or other containers in the pod. The `server` and `task-worker` components of the `infrahub` and `infrahub-enterprise` example drivers now accept `command`, and the `simple-app`, `infrahub` and `infrahub-enterprise` example drivers move to versions 3, 4 and 3. Adding or changing `command` or `args` on a component without a component container is now rejected with `COMPONENT_CONTAINER_NOT_DECLARED` (metadata `override` set to `command` or `args`); removing a stored value, or sending the same value again, is still accepted. The deployment's Configuration editor hides the Command and Args editors for such a component, shows stored values read-only as JSON lists, marked "not applied", with a remove button, and explains that the component accepts no overrides instead of offering "Add override"; the new `ComponentContainerOverrides.isApplicable` field in the API and the SDK reports whether a stored override applies. The Command and Args editors explain what they replace and what happens with no rows, warn about an empty command element, and name each input for screen readers. The Component Overrides card on the Configuration tab now lists the stored `command` and `args` of each component as JSON lists, with an "applied" or "not applied" badge, and lists every block stored on a component the driver no longer declares, not only image overrides. `styrminctl deployments apply` now also warns on stderr about `command` and `args` that it stores but that the driver version does not apply; it prints one warning per component that names the kinds of override and says to remove them from the manifest or to load a driver version that declares a component container for the component, and the SDK lists the kinds per component in the new `ApplyOutcome.inapplicable_overrides`, next to `ApplyOutcome.inapplicable_components`. ([#457](https://github.com/opsmill/styrmin/issues/457))
- Changed `styrmin config show` to leave out credentials: `admin_password`, the database `db_password` and `db_url`, and the `token` of the `[kubernetes]`, `[driver]` and `[agent_code]` sections. A value in `styrmin.toml` takes precedence over its `STYRMIN_*` environment variable, so an output of `styrmin config show` saved as `styrmin.toml` would otherwise fix these credentials in the file, and a credential rotated in the environment would have no effect.

### Fixed

- Fixed a restore of a Velero backup that no longer exists waiting until the restore timeout (two hours by default): Velero's `FailedValidation` phase now ends a backup or a restore at once, and the "Run the Velero restore" step and the restore's error message show Velero's validation errors. A backup or restore that Velero ends without a failure reason, such as a `PartiallyFailed` backup, now has the error of its failed step as its error message instead of an empty one. ([#2](https://github.com/opsmill/styrmin/issues/2))
- Fixed a failed `runJob` Job being reported as an unrelated `KeyError` instead of the Job's failure. ([#2](https://github.com/opsmill/styrmin/issues/2))
- Fixed updates and upgrades being reported ready before FluxCD applied the new release: the operator now waits until FluxCD reports the HelmRelease's current generation Ready, shows FluxCD's reason while it waits, fails the deployment when FluxCD has used all its retries (`Stalled`) or reports its rollback of a failed upgrade as ready, and counts its readiness timeout from the start of each rollout instead of from the creation of the deployment, so a failed update or upgrade now ends `FAILED` instead of `RUNNING`. ([#2](https://github.com/opsmill/styrmin/issues/2))
- Fixed the backup size (`sizeBytes` in GraphQL, `size_bytes` in the SDK and `styrminctl backups`, and the size column in the web UI) holding a count of Velero item operations instead of bytes. A completed backup now records the bytes of volume data that Velero read, before deduplication and compression, and the size stays empty when the backup captured no volume data. To hold sizes above 2 GiB, `sizeBytes` now uses a new `BigInt` GraphQL scalar (a JSON number) instead of `Int`, and a database migration widens the `backup.size_bytes` column to `BIGINT`. The Helm charts now grant read access to Velero `podvolumebackups`. ([#136](https://github.com/opsmill/styrmin/issues/136))
- Fixed the dedicated ingress controller of an environment staying on the cluster after the last application in that environment was deleted. Styrmin now removes the ingress controller once that application reaches `deleted`, and installs a new one when you deploy into the environment again. While the removal runs, new deployments into the environment are rejected with a message to retry once it completes. ([#252](https://github.com/opsmill/styrmin/issues/252))
- Fixed the environment list and environment detail pages showing the ingress controller of a dedicated ingress as one of your applications. The deployment list, the application count and the environment status now include only the applications you deployed, so an ingress controller that fails no longer marks the environment as failed. ([#253](https://github.com/opsmill/styrmin/issues/253))
- Fixed backups disappearing from a deployment's Backups tab and from `styrminctl backups list` after the deployment got a new instance. Backups taken before an upgrade, a config edit or an environment config change now stay listed, and a deleted deployment keeps its list of backups. ([#304](https://github.com/opsmill/styrmin/issues/304))
- Fixed updating or upgrading a deployment whose namespace was never created, for example because its create task stopped early: the task now creates the namespace instead of failing with `namespaces "styrmin-<deployment-id>" not found`. ([#313](https://github.com/opsmill/styrmin/issues/313))
- Fixed a deployment that sometimes ran the configuration of an earlier change after two changes made one after another, on the deployment page, with `styrminctl` or through the API. Each change starts its own workflow, and the workflow of the earlier change could write the `StyrminDeployment` last. A deployment whose older configuration could not start then stayed `pending`. Styrmin now numbers each deployment's instances in the order it saves them and records the number on the `StyrminDeployment`, in the `styrmin.io/instance-sequence` annotation. A workflow leaves a `StyrminDeployment` that holds a higher number unchanged, and the task of the earlier change ends as `superseded`. ([#386](https://github.com/opsmill/styrmin/issues/386))
- Fixed `styrminctl deployments apply` checking component config against the driver version a deployment moves away from. For an existing deployment, `apply` now sends the config, parameters and version in one request, so the config is checked against `spec.version` and the newest loaded driver version that supports it, one task reconciles the change, and a rejected apply leaves the deployment unchanged and is reported as `failed` with the server's error code. A manifest can now move a deployment onto a driver version that declares component containers and add component env vars in the same apply. Upgrade the Styrmin server before or together with `styrminctl` and the SDK: against an older server, `apply` fails with a message that says to upgrade the server. ([#388](https://github.com/opsmill/styrmin/issues/388))
- Fixed the deployment state becoming `running`, and `styrminctl deployments apply --wait` returning, while an upgrade's driver hook was still running, for example between the hook's `stop_components` and `start_components` calls. ([#405](https://github.com/opsmill/styrmin/issues/405))
- Fixed the dedicated ingress setting being read two ways: an empty `dedicated_ingress` (`{}`) now deploys the per-environment ingress controller with default values, as it already did for the application Ingress. A cluster created without `dedicated_ingress` no longer stores `{}`, and the database upgrade removes the `{}` that existing clusters stored, so their deployments keep running without a dedicated controller and their Ingress now uses the cluster `ingress_class`. ([#409](https://github.com/opsmill/styrmin/issues/409))
- Fixed restores of deployments with a MariaDB or MongoDB component ending as `failed` when the database took more than 5 seconds to accept connections after Velero restored its pod. The restore hooks now retry loading the dump every 2 seconds for up to 2 minutes, instead of loading it once after a fixed 5-second wait. ([#412](https://github.com/opsmill/styrmin/issues/412))
- Fixed saving a deployment's configuration from the UI when its scheduling sets an `ephemeral_storage` request or limit, or an affinity rule with a `deployment_ref`: the editor sent stored keys that the API refused. ([#423](https://github.com/opsmill/styrmin/issues/423))
- Fixed environment updates not changing the environment's dedicated ingress controller: when `updateEnvironment` turns the environment's `dedicated_ingress` on or changes its values, Styrmin now creates the controller or redeploys it with the new values, and redeploys the applications onto it once it is `RUNNING`. Submitting the environment config again redeploys a controller left with the values of an earlier environment update. ([#424](https://github.com/opsmill/styrmin/issues/424))
- When one apply sets an image override or env vars and changes the application version, the driver's upgrade action now uses them. Before, its first Job could run with the previous image repository and without the new env vars, because the action read the component's workload before the new values reached it. An env var removed in the same apply still reaches the upgrade action's Jobs. ([#431](https://github.com/opsmill/styrmin/issues/431))
- Fixed an upgrade to another driver version that changes env vars or image overrides but not the Helm values: the pods now get the new env vars and images, where FluxCD reported the release in sync and kept the old ones. ([#432](https://github.com/opsmill/styrmin/issues/432))
- Fixed changes to env vars or image overrides that reached the cluster while FluxCD was still upgrading the previous change of the deployment: FluxCD now applies them, where the pods kept the values of the previous change until the next change. ([#433](https://github.com/opsmill/styrmin/issues/433))
- Fixed an environment config update in which one deployment whose redeploy failed discarded the redeploys started before it in the same update: those deployments now keep their new instance and their task, as in a cluster config update. ([#452](https://github.com/opsmill/styrmin/issues/452))
- Fixed the deployment's Configuration editor leaving **Review & apply** disabled when the only change was to the `command` or `args` of a component, so such a change, including the removal of a stored value, could not be submitted. ([#457](https://github.com/opsmill/styrmin/issues/457))
- Fixed `styrmin.toml` rejecting the field names that `styrmin config show` writes for the database settings, the Kubernetes connection settings (`config_mode`, `host`, `token`, `ca_cert`) and `session_cookie_secure`. Also fixed `styrmin config show` writing enum values, such as `db_type` and `config_mode`, as lists of characters. The output of `styrmin config show` now loads back as a config file.
- Fixed environment clones that could delete the source deployment's PostgreSQL StatefulSet and Services: the restored Helm release storage is now pointed at the clone's namespace before the clone's HelmRelease is created.
- Fixed environment clones that sometimes ended as Failed after a clean restore: discarding the restored copy of the source deployment could remove the clone's NetworkPolicies, Secrets and Services while the restore was re-applying them.
- Fixed restores on clusters that run Cilium sometimes leaving a restored pod unreachable from pods on other nodes, until someone deleted the pod: backups and restores no longer include the per-pod network records (`CiliumEndpoint`) that Cilium recreates when a pod starts.
- Fixed the **Configuration** tab of the environment page treating an empty `dedicated_ingress` (`{}`) as off. The tab showed "Using default ingress controller." and let you save environment variables or the backup retention. That save sent `dedicatedIngress: null`, which turns the environment's own `dedicated_ingress` off, so Styrmin removed the environment's dedicated ingress controller unless the cluster sets `dedicated_ingress`. The tab now shows "Dedicated ingress controller on, default values." and blocks saving, as it does for any other `dedicated_ingress` value.
- Fixed the backup storage location forms showing "[object Object]" instead of the error message under a field that fails validation. This affected the dialog that creates a backup storage location and the credentials form on the backup storage location page.
- Fixed the cluster detail page so it shows every cluster setting: the dedicated ingress with its service settings and defaults, the external URL and DNS settings, storage, runtime and scheduling, backup retention, and the cluster capabilities.

## [Styrmin - v0.1.47](https://github.com/opsmill/styrmin/tree/v0.1.47) - 2026-10-07

### Added

- Added per-component image overrides: a deployment can run a custom or patched build on one component, without forking its driver, by setting one image reference on that component. Styrmin applies it after the Helm chart renders, to the component container the driver declares; a `{{ app.version }}` token follows the deployment's application version, while a literal tag or digest pins the image, the upgrade dialog warns about pinned overrides before an application version change, and `styrminctl deployments apply` names them in its output when it changes the version. Available as `ComponentConfigInput.image` on `deploy` and `updateDeployment`, the `Deployment.componentImageOverrides` read field (stored reference, resolved reference, and whether it applies), `components[].image` in `styrminctl deployments apply` manifests, `ApplyOutcome.pinned_image_components` in the SDK, and an **Image** field per component in the deployment's Configuration editor. Invalid references, unknown components, and components without a component container are rejected before anything is deployed, and an application version upgrade that would make a stored override invalid is rejected before any lifecycle action runs. ([#20](https://github.com/opsmill/styrmin/issues/20))

### Changed

- Changed the agent and operator settings (poll retries and intervals, status poll interval, reconcile interval, deployment ready timeout, peering, deleted StyrminDeployment retention and janitor interval) to load with the other Styrmin settings: they keep their environment variable names, can also be set in `styrmin.toml` under `[agent]` and `[operator]`, and appear in `styrmin config show`. Removed `STYRMIN_OPERATOR_HR_READY_TIMEOUT`, which had no effect. A value below 1 for a poll interval, the reconcile or janitor interval, or the deployment ready timeout is now rejected when the settings load, instead of making a poll loop run without waiting. ([#16](https://github.com/opsmill/styrmin/issues/16))
- Changed `get_component_images` to return the component container's image first (the other images keep their pod-template order), so a driver action that takes `images[0]` sees the component's image override; the example drivers' `upgrade` actions now do so instead of matching an image name. A driver that declares a component container name its chart does not render now fails the deployment with `COMPONENT_CONTAINER_NOT_FOUND`, naming the component and the container, as soon as env vars or an image override target that component, instead of the Helm release failing on an added container without an image; Styrmin never adds a container. Clear every image override before rolling Styrmin back below this release: older releases reject the `image` key in a deployment's config. ([#20](https://github.com/opsmill/styrmin/issues/20))
- Upgraded Prefect to 3.8.6 (from 3.6.25). The Helm chart now installs the Prefect server 3.8.6 chart (`prefect-server` 2026.9.14141910), and the server pod gets the chart's default startup, liveness and readiness probes. The local `docker-compose.yml` uses the `prefecthq/prefect:3.8.6-python3.14` image. ([#236](https://github.com/opsmill/styrmin/issues/236))

### Fixed

- Fixed Prefect workers holding database connections open after backup, restore, environment clone and reconcile flows; each flow step now returns its connection to the pool when it ends. ([#140](https://github.com/opsmill/styrmin/issues/140))
- Fixed user actions running the driver's branch tip instead of the commit the driver version was loaded from. Driver versions loaded from now on run the code at their recorded `sourceCommitSha`, and reloading a driver at a newer commit no longer overwrites the actions of earlier versions. ([#375](https://github.com/opsmill/styrmin/issues/375))
- Fixed driver actions failing with "Authentication is required" when they call `stop_components`, `start_components` or `upgrade_deployment_version`. Upgrades of bundled-driver deployments ended with a failed task, and the steps after the first call (such as the Infrahub database migration) did not run. Each reconcile now gives its actions a short-lived token for the built-in `styrmin-actions` user and revokes the token when the reconcile ends. ([#381](https://github.com/opsmill/styrmin/issues/381))
- Fixed a deployment reading `running` instead of `restoring` while a restore of it is in progress: an agent status report sent before Velero finished replaced the `restoring` state, so the guards that refuse other operations on a restoring deployment did not apply during that time. A restore whose workflow could not be dispatched is now marked `failed`, together with its deployment, instead of staying `pending` and keeping the deployment in `restoring`. A second restore of a deployment is now refused while a restore of it into another namespace is still in progress. ([#389](https://github.com/opsmill/styrmin/issues/389))
- Fixed `styrmin config show` dropping the `[section]` headers from its TOML output, which made the output invalid TOML.

## [Styrmin - v0.1.46](https://github.com/opsmill/styrmin/tree/v0.1.46) - 2026-10-04

### Removed

- Removed the `component_env_vars` driver template filter. A driver `values.j2.yml` that still calls it now fails rendering with an error that names the [migration guide](https://styrmin.pages.dev/docs/drivers/migrating-env-vars), so a deployment pinned to an unmigrated driver version fails on its next change (including the redeploy an environment env var edit triggers) until it is upgraded to a driver version that declares component containers. ([#385](https://github.com/opsmill/styrmin/issues/385))

### Added

- Added environment clone: one action copies a live environment into a brand-new environment on the same cluster, built from a fresh backup of the source, with a choice of which deployments to include and a clone-time config override (set or clear captured config fields) so the copy can be made safe before it starts. Available as the `cloneEnvironment` mutation (ADMIN) plus the `environmentClone` / `environmentClones` queries, `client.environment_clones` in the SDK, the `styrminctl env-clones` command group, and a **Clones** tab with a clone dialog on the environment detail page. A clone's status is derived from its backup, the environment it created and the restores into that environment's deployments; deleting the created environment discards the clone. ([#6](https://github.com/opsmill/styrmin/issues/6))
- Added environment-level backup and restore: one action snapshots an environment — its config plus the declared state and a constituent backup of every eligible deployment — and one action restores it in place. Available as the `createEnvironmentBackup`, `restoreEnvironmentBackup` (ADMIN, since it rewrites the environment's config) and `deleteEnvironmentBackup` mutations plus the `environmentBackup(s)` / `environmentRestore(s)` queries, `client.environment_backups` in the SDK, the `styrminctl env-backups` command group, and a **Backups** tab on the environment detail page. An environment backup's status is derived from its constituents and adds a `PARTIAL` outcome; existing per-deployment backups are unaffected. ([#7](https://github.com/opsmill/styrmin/issues/7))

### Changed

- Changed how env vars reach pods: a driver now declares one component container per component (`components.<name>.container`), and Styrmin merges the environment, deployment, and component env vars into that container by name after the Helm chart renders, so the chart's own env defaults are kept and a user value replaces a chart entry of the same name. User env vars no longer reach chart Jobs, init containers, or other containers; adding or changing a component env var on a component without a component container is rejected with `COMPONENT_CONTAINER_NOT_DECLARED`; and on every update Styrmin replaces each HelmRelease spec key it writes (keys it never writes, such as `spec.suspend`, are kept), so env values written by an old driver template no longer linger. Every example driver declares its component containers. Rolling Styrmin back below this release stops env var injection for drivers already migrated. ([#385](https://github.com/opsmill/styrmin/issues/385))

### Fixed

- Fixed `createUser`, `updateUser`, `createGroup`, and `updateGroup` returning an opaque "An internal error occurred" when a `groupIds`/`memberIds` entry is not a valid UUID: malformed IDs now return a typed `VALIDATION_ERROR` naming the offending value. ([#351](https://github.com/opsmill/styrmin/issues/351))
- Fixed the example `slurpit` driver passing its hard-coded database credentials and warehouse tokens to the slurpit chart as a list: the chart expects a map, so its ConfigMaps held keys `0`, `1`, … and neither that wiring nor the chart's own env defaults reached the containers. Fixed the example `infrahub` and `infrahub-enterprise` drivers dropping the Prefect server chart's env defaults (`PREFECT_UI_SERVE_BASE`, plus `PROMETHEUS_MULTIPROC_DIR` on the community chart).

## [Styrmin - v0.1.45](https://github.com/opsmill/styrmin/tree/v0.1.45) - 2026-09-25

### Added

- Added a `deployment(name, environmentId)` GraphQL query that resolves a non-internal, non-soft-deleted deployment by its natural identity, exposed in the SDK as `client.deployments.get_by_name(name, environment_id=...)`. The existing `deployment(deploymentId)` lookup is unchanged.
- Added declarative deployment management via `styrminctl deployments apply`: author YAML manifests (`apiVersion: styrmin/v1`, `kind: Deployment`) and apply them with `styrminctl deployments apply -f <path>` to create or update deployments by their natural identity `(name, environment)`. Supports single files, directories, multi-document YAML, multiple `-f` flags, and CLI/env-var overrides; the optional `--wait` flag blocks until each deployment reaches a terminal state.

### Changed

- Changed the `styrmin-agent` Helm chart to default `image.tag` to the chart's `appVersion` instead of the hardcoded `latest`, matching the `styrmin` chart, so a default install of a released chart pins the agent to that release's image rather than tracking a floating tag. Installs that need a locally-built or otherwise floating image must now set `styrmin-agent.image.tag` explicitly — see `helm/styrmin/README.md` ("Running against a locally-built image").
- Changed the `velero` subchart from 8.3.0 to 12.1.0 (Velero 1.15.2 to 1.18.1) and `velero-plugin-for-aws` from v1.11.1 to v1.14.2. On `helm upgrade` the chart's CRD job applies the new Velero CRDs and the Velero server and node-agent pods restart once.
- Changed the local demo and the E2E suite to provision [Garage](https://garagehq.deuxfleurs.fr/) instead of MinIO as the in-cluster S3-compatible store Velero writes backups to: `uv run invoke cluster.minio` becomes `uv run invoke cluster.garage`, the manifest moves from `dev/local/minio.yaml` to `dev/local/garage.yaml`, and the bootstrapped backup storage location points at `http://garage.styrmin.svc:3900` (region `garage`). Nothing about the product's S3 support changes — any S3-compatible bucket still works.

### Fixed

- Fixed the light/dark theme toggle being reachable only from the Environments page: it now lives in the shared application header, so it is available from every page — Environments, Clusters, Deployments, Drivers, Backup Storage, Settings, Profile — and from the login screen. ([#331](https://github.com/opsmill/styrmin/issues/331))
- Fixed renaming a backup storage location to a name already in use failing with an opaque "An internal error occurred": the update path now rejects the duplicate with a typed `ALREADY_EXISTS` error, matching the create path. ([#350](https://github.com/opsmill/styrmin/issues/350))
- Fixed Velero backup-repository maintenance, which had never run in any Styrmin install: Velero resolves its own Deployment by the hardcoded name `velero` to build the kopia maintenance Job, but the `velero` subchart named it `<release>-velero`, so every cycle failed with `Deployment.apps "velero" not found`, kopia never pruned, and the data behind expired backups was never reclaimed from the bucket. `helm/styrmin/values.yaml` now pins `velero.fullnameOverride: velero`. **Upgrading:** the Velero Deployment, Service, ServiceAccount, and ConfigMaps are renamed, so `helm upgrade` replaces them and the Velero pod restarts once; update anything referring to the old names (`deployment/<release>-velero`, dashboards, scrape configs) to `velero`. The PVC-patch ConfigMap is now `velero-restore-pvc-patch`; Restores created before the upgrade keep pointing at the old name and cannot be re-driven, but Restores are one-shot objects and new ones are unaffected. Helm creates the renamed Deployment before it deletes the old one, so two Velero servers overlap for a few seconds; do not upgrade while a backup or restore is in flight.
- Fixed Velero's idle log volume, now roughly 5x quieter: `--backup-sync-period` and `--store-validation-frequency` default to `5m` instead of Velero's 1m. Each cycle spawned and killed an object-store plugin process whose teardown logs a spurious error ([velero#7892](https://github.com/vmware-tanzu/velero/issues/7892)), so the default cadence buried real backup logs under ~7 noise lines a minute per BackupStorageLocation. Styrmin names the BSL on every backup and tracks backup state in its own database, so neither loop was load-bearing.

### Housekeeping

- Replaced hand-edited changelog entries with towncrier newsfragments: `CHANGELOG.md` is now generated at release time from files in `changelog/`, using the same towncrier configuration and rules as infrahub.
