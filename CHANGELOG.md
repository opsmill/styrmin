## [Styrmin - v0.1.59](https://github.com/opsmill/styrmin/tree/v0.1.59) - 2026-11-13

### Added

- Added service ingress overrides. A deployment can set the ingress class, the FQDN suffix, or both, for one service that its driver declares `scope: external`. The override goes in a manifest (`spec.config.services`), in the `services` field of the GraphQL config input (`ServiceConfigInput`), or in the Settings tab and the deploy form. The other services of the deployment keep the resolved class and suffix. An overridden Ingress carries only the ingress class: the `ip_whitelist` of the deployment and the external DNS record do not apply to it, and the application address is not on it. Styrmin refuses an override on a service that Styrmin builds no Ingress for (an internal service, or an external service of kind `tcp` or `udp`) or that the driver version does not declare (`SERVICE_INGRESS_NOT_BUILT`, `UNKNOWN_SERVICE_INGRESS_OVERRIDE`). Styrmin also refuses a driver version change that would remove the service, make it internal, or make its kind `tcp` or `udp` while an override is stored (`SERVICE_INGRESS_OVERRIDE_WOULD_BE_DROPPED`). Each error names the service. A manifest that sets `spec.config` keys and no `services` clears the stored overrides, and `styrminctl deployments apply` prints a `warning:` line that names the services. See [Service ingress overrides](https://styrmin.pages.dev/docs/concepts-and-architecture/service-ingress-overrides). ([#598](https://github.com/opsmill/styrmin/issues/598))

### Changed

- Changed the meaning of `scope: external` for a service of a driver (breaking change). Styrmin now builds one Ingress for each external service of kind `http` or `https`. A driver that declares a service `external` and also renders its own Ingress for it gives that service two Ingresses on the same host. The effect starts when a deployment runs this Styrmin release, at its next reconcile, not only when its driver version changes. Of the drivers that OpsMill ships in `driver/examples`, only `generic-app` driver version 1 renders its own Ingress for an external service, so only deployments of that version get a second Ingress. An apply error on an Ingress now fails the deploy flow, so an ingress controller that rejects a duplicate host and path could fail the deploy flow of such a deployment. This is plausible and has not been verified. The `generic-app` driver version 2, the `infrahub` driver version 6 and the `infrahub-enterprise` driver version 5 declare an external service and render no Ingress for it, and the `task-manager` service of both Infrahub drivers is now external. When a running Infrahub deployment moves to the new driver version, the Prefect UI Ingress moves from the Helm chart to an Ingress that Styrmin builds. On a local vCluster with the operator pass every 60 seconds, the Prefect UI host answered HTTP 404 for about 7 seconds and about 12 seconds (2 samples, `infrahub-enterprise` from driver version 4 to 5). With the pass every 5 seconds, no request failed (2 samples). The length depends on when the next operator pass falls, and it was not measured on other systems or for `infrahub` version 6. A driver author removes the Ingress from the chart values of the driver, or declares the service `internal`. How many drivers outside this repository are affected is not known. See [Migrate a driver whose external service renders its own Ingress](https://styrmin.pages.dev/docs/drivers/migrating-external-service-ingress). ([#598](https://github.com/opsmill/styrmin/issues/598))

### Fixed

- Fixed two passes of the operator writing different `styrmin.io/release-reference` labels on the same Ingress, Service, Secret and NetworkPolicy objects of a deployment. The HelmRelease timer used an empty release reference, because the HelmRelease that Styrmin creates has no such label, and the StyrminDeployment timer used the real one. Each timer replaced the objects that the other had written, so the label changed between the two values every few seconds. The HelmRelease timer now uses the release reference of the deployment when the HelmRelease has no label, and the builder of these objects does the same, so each object keeps one label value. The change of the label was measured on all four kinds in the end-to-end runs of the service ingress override change. Whether released versions show it for a Service, a Secret or a NetworkPolicy was not checked. In the same runs, the operator still rewrote Services about every 5 seconds, and the cause is not known.

## [Styrmin - v0.1.55](https://github.com/opsmill/styrmin/tree/v0.1.55) - 2026-10-28

### Added

- Added `client.deployments.wait_for_task()` to the Python SDK. It takes the task that a create, update, scale, upgrade, deletion, start or stop of components, or job returns, and waits until the change has finished: until the task result, which covers the task's hooks and the operator's rollout, is final, then until the deployment is `running`, or `deleted` after a deletion. It returns whether the change succeeded and, when it did not, the failed step, the deployment status or the timeout. ([#545](https://github.com/opsmill/styrmin/issues/545))
- Added `environments.get_pod_statuses()`, `environments.get_services()` and `clusters.get_pod_statuses()` to the Python SDK. A script now reads the pod statuses of every deployment of an environment or of a cluster, or the services of every deployment of an environment, in one call instead of one call per deployment. Each method takes an ID or a name, as `environments.get()` and `clusters.get()` do, and raises `ResourceNotFoundError` when nothing matches. ([#547](https://github.com/opsmill/styrmin/issues/547))

### Changed

- Changed the FluxCD controllers that the agent chart installs from helm-controller v1.6.5 and source-controller v1.9.6 (Flux v2.9.6) to helm-controller v1.7.1 and source-controller v1.10.1 (Flux v2.10.0). When a change of env vars or image overrides fails before Helm stores a release, for example because the component container is not found, helm-controller now keeps the HelmRelease not ready and tries again, instead of reporting the previous release in sync ([fluxcd/helm-controller#1607](https://github.com/fluxcd/helm-controller/issues/1607)). The agent therefore no longer reads FluxCD's Kubernetes Events, and its ClusterRole no longer allows `list` on `events`. After FluxCD rolls back a failed upgrade, it now tries again until it has used its 3 retries, instead of reporting the rolled-back release ready: a rollout whose pods cannot start still shows `Error` from the readiness timeout on, and becomes `Failed` with the message `Failed to upgrade after 4 attempt(s): …` about 20 minutes after the change with the default timeouts, instead of `Failed` with `FluxCD rolled the release back after release v<N> failed` right after the first rollback. The FluxCD project supports Flux v2.10 on Kubernetes 1.35.2 and later.
- Changed the documentation links in error messages and in the Helm chart README to docs.styrmin.app.
- Changed the web UI favicon, the logo at the top of the sidebar, the sign-in page and the documentation site logo, favicon and link preview image to the Styrmin logo, and set the documentation site address in link previews to docs.styrmin.app.

### Fixed

- A restore of the backup of an earlier instance now makes that instance the deployment's active instance, with its application version, config, parameters and driver version. Before, the deployment page and `styrminctl` kept showing the later version while the cluster ran the earlier one, a backup taken afterwards was listed at the later version, and the next config edit applied the later version over the restored one. ([#426](https://github.com/opsmill/styrmin/issues/426))
- A deployment that is being deleted no longer becomes `deleted` while Kubernetes is still removing its namespace. The agent's status reporter set `deleted` as soon as the deployment's `StyrminDeployment` was gone, but Kubernetes deletes that resource with the rest of the namespace's contents, before it removes the namespace itself. ([#545](https://github.com/opsmill/styrmin/issues/545))
- The `podStatuses` query no longer returns the pods of deleted deployments when it filters by `environmentId` or `clusterId`. The agent stops reporting a deployment once it is deleted, so the pods of its last report could stay in these lists. ([#547](https://github.com/opsmill/styrmin/issues/547))
- Fixed failed deployments that did not say why a pod could not be scheduled or why an init container failed. The failed "Install or upgrade the HelmRelease" or "Wait for the deployment to be ready" step, `styrminctl tasks get`, the Pods tab and `podStatuses` now show the scheduler's reason and message for a pod that is not scheduled, list init containers and sidecars with their state and restarts, name an init container that is still running and a sidecar that is not ready, keep the kubelet's message of a waiting container, and name any waiting or ended container reason instead of eight fixed ones. ([#574](https://github.com/opsmill/styrmin/issues/574))

## [Styrmin - v0.1.53](https://github.com/opsmill/styrmin/tree/v0.1.53) - 2026-10-23

### Security

- Stopped `createRestore` from deleting a namespace that the user names. Before, a user with the `READ_WRITE` role could pass any namespace as `targetNamespace`, for example `kube-system`, and the restore deleted that namespace and restored the backup into it: with the agent chart's default values, the restore Job runs as `styrmin-service-account`, whose ClusterRole may delete any namespace. Versions v0.1.19 to v0.1.50 are affected unless an operator changed that service account or its ClusterRole; v0.1.0 to v0.1.18 took `targetNamespace` too and checked no role on `createRestore`. A restore now lands only in the namespace `styrmin-<deployment id>` of the deployment the backup was taken of. The restore flow also fails a restore whose namespace is not that one before it changes anything in the cluster, which covers a restore that an earlier version queued before the upgrade and a flow run started directly through the Prefect API. ([#532](https://github.com/opsmill/styrmin/issues/532))

### Removed

- Removed the `targetNamespace` and `targetInstanceId` arguments from the `createRestore` mutation, the `target_namespace` and `target_instance_id` parameters from `create_restore()` in the Python SDK, and the `--target-namespace` option from `styrminctl backups restore`: Styrmin restores a backup into the deployment it was taken of, in that deployment's namespace, and records that deployment's active instance on the restore. Apart from an environment clone, Styrmin offers no way to restore a backup into another deployment until deployment clone, a separate feature, ships. Before you upgrade, read the upgrade steps under "Migration" in [A restore lands only in the deployment its backup was taken of](https://styrmin.pages.dev/docs/changelog#restores-no-longer-delete-a-namespace-that-the-caller-names): upgrade the server, `styrminctl` and the Python SDK together, reload the web pages that were open during the upgrade, remove the arguments and the option above from your scripts and requests, and run `styrminctl backups restore <backup-id>` with the backup id alone, because the command now refuses a backup id combined with `--target-deployment`, `--target-deployment-id`, `--target-instance-id` or `--environment`, which work only with `--last`. ([#532](https://github.com/opsmill/styrmin/issues/532))

### Added

- Added a link to the home page on the Styrmin logo and name at the top of the sidebar. ([#198](https://github.com/opsmill/styrmin/issues/198))
- Added a GraphQL Sandbox link at the bottom of the sidebar. It opens the interactive GraphQL editor that the server provides at /graphql in a new tab. ([#199](https://github.com/opsmill/styrmin/issues/199))
- Added `deployment_id` to the instance of each backup that `list_backups()` returns in the Python SDK. ([#532](https://github.com/opsmill/styrmin/issues/532))

### Changed

- Changed `styrminctl backups restore --last` to treat a deployment the way the server does: `--target-deployment` and `--target-deployment-id` no longer refuse a deployment without an active instance, and `--target-instance-id` now asks for confirmation, as the deployment options already did, when the chosen backup was taken of an earlier instance of its deployment or at another application version; `--yes` skips the question, and without a terminal the command refuses unless you pass `--yes`. The Restore dialog of the web app now shows the deployment and the namespace the backup is restored into as text instead of a read-only field, and the restore warning for a deployment without an active instance no longer says that Styrmin keeps its current instance. The "Restore already in progress" error now says to wait until that restore completes or fails and where to view its status. ([#532](https://github.com/opsmill/styrmin/issues/532))

### Fixed

- Fixed an in-place restore that deleted the namespace the caller named and restored the backup into it, which could be the namespace of another deployment, instead of the namespace of the deployment the backup was taken of. ([#532](https://github.com/opsmill/styrmin/issues/532))
- Fixed applications of one environment being unable to connect to each other's declared services on clusters that enforce network policies: Styrmin now lets the other deployments of the environment connect to each service that a driver declares, on the service's port only, and lets each deployment connect to the rest of its environment. Styrmin's policies keep components that serve no declared service, and other environments, closed. ([#557](https://github.com/opsmill/styrmin/issues/557))

## [Styrmin - v0.1.51](https://github.com/opsmill/styrmin/tree/v0.1.51) - 2026-10-21

### Fixed

- Fixed the actions of drivers loaded with `styrminctl drivers load-local-version`, which never ran: a deployment created or upgraded from such a driver now runs its setup and upgrade actions, and a hook whose declared action has no registered flow now fails with an error that tells you to load the driver again, instead of being skipped. The Styrmin agent runs these actions from the same path as the server, so a driver that only the server container holds now fails its actions with an error that names the path and the agent pod and says how to put the driver there; the errors no longer name an image, because an action's `image:` has no effect. Load your local drivers again after you upgrade, to register their actions. Deployments created from local drivers before this fix never ran their setup actions, and Styrmin does not run them now. A load from a local directory of a driver that declares actions is now refused when the path is relative or when an action's `location` is in another file than `actions.py`, and a load from git or from a local directory is refused when the driver declares two actions for one hook and mode; the check before each action covers `actions.py` but not the modules that it imports. When the flow run of an action crashes, its hook step now shows the first `ERROR` log line of that run, with the action's API token and common forms of secrets replaced by `<redacted>`; every signed-in user who can read the task can read it, so actions must not write secrets to their logs. Deleting a deployment whose create failed before its `StyrminDeployment` was written, for example at the setup pre-hook, now deletes it instead of returning "An internal error occurred"; while a change of such a deployment is still applied, the delete is refused with a message that names the deployment and says to delete it again when its status is running or failed. When an upgrade fails because an upgrade action has no registered flow, the deployment keeps its version, and `styrminctl deployments update-version` and `styrminctl deployments apply` print the error and exit with code 1, `apply --wait` included. A second `execute_commands` call on the same deployment, for example in the next upgrade with the bundled `simple-app` or `infrahub` drivers, now deletes the Job that the earlier call left, once that Job has ended, and runs its commands, instead of failing because a Job of that name already exists; the hook step names the deleted Job. A Job of that name that is still running, for example the migration Job of another upgrade of the same deployment, is never deleted: the action fails and tells you to wait for the Job to end and request the change again. ([#372](https://github.com/opsmill/styrmin/issues/372))
- Fixed the Python SDK dropping the extensions of a GraphQL error: the exceptions it raises, such as `OperationFailedError`, now give all the extensions that the server returned in an `extensions` attribute, so a program can read, for example, the `path` of a refused affinity term or the `deployments` of a refused clone request without parsing the message. ([#522](https://github.com/opsmill/styrmin/issues/522))
- Fixed applications in a cloned environment that reached the source environment's deployments by short service name: the restore of each cloned deployment restored the source's service aliases, which pointed to the source environment. A clone now restores none of them and writes the aliases of the new environment, so applications in the clone reach the clone's deployments, and a deployment that was not cloned cannot be reached by short service name from the clone. A clone now also reports a deployment whose restore failed as failed, with the restore's error as the reason, where it reported it as cloned before. When a clone cannot write a deployment's service aliases, that deployment's restore fails with the error; see [Watching a clone](https://styrmin.pages.dev/docs/concepts-and-architecture/backups-and-restores#watching-a-clone-and-what-its-status-means) to write them afterwards. ([#530](https://github.com/opsmill/styrmin/issues/530))
- Fixed a restore and an environment clone leaving the deployment's namespace without its `styrmin/environment_id` and `styrmin/deployment_id` labels. A network policy that selects namespaces by them, such as the one that lets a shared ingress controller reach the application, no longer matched the namespace, so the restored application was unreachable while Styrmin showed it running. The restore now puts the labels back, and a clone gets the labels of its own environment and deployment. ([#542](https://github.com/opsmill/styrmin/issues/542)) ([#542](https://github.com/opsmill/styrmin/issues/542))

## [Styrmin - v0.1.50](https://github.com/opsmill/styrmin/tree/v0.1.50) - 2026-10-19

### Security

- Stopped passing the S3 access key and secret key of a backup storage location to the `sync-bsl-create` and `sync-bsl-update-credentials` flows as flow-run parameters, which the Prefect server stores and shows in its UI and API. Styrmin now saves the keys in a Prefect Secret block named `styrmin-bsl-<id>-credentials`, the flows read them from it, and deleting the location deletes the block. Flow runs started by earlier versions still show the keys until Prefect deletes them; to make those keys useless, rotate them in your object storage and update the location. ([#497](https://github.com/opsmill/styrmin/issues/497))
- Stopped loads from git from reading files outside the cloned repository. Before, a repository whose `driver.styrmin.yml`, `values.j2.yml` or `actions.py` was a symlink to a path on the Styrmin server, such as `values.j2.yml -> /etc/...`, made the server read that file and return it in the driver version, for example in `helmChart.valueTemplate`. Every load from git, also from the repository root, now fails when the driver directory is a symlink to a path outside the repository, when one of these three files is a symlink to a path outside its driver directory (the whole repository for a load from the root), or when one of them cannot be followed, such as a symlink loop. Reloading a repository that has such a symlink now fails with a message that names the file; replace the symlink with the file it points to. Error messages of git loads no longer show the user info, such as `user:token@`, of any URL that a clone error repeats. See [Loading a Driver](https://styrmin.pages.dev/docs/drivers/loading-drivers#refused-driver-directories-and-error-messages). ([#517](https://github.com/opsmill/styrmin/issues/517))

### Removed

- Removed the `replicas_server` and `replicas_task_worker` parameters from the `infrahub` example driver (version 5) and the `infrahub-enterprise` example driver (version 4): set a replica override on the `server` or `task-worker` component instead. A deployment that stores either parameter at its old default (`1` and `2`) moves to the new versions without a manual step. A deployment that stores another value is rejected with `RETIRED_PARAMETER_VALUE` until the same request, or an earlier one, carries the value over as a replica override and resets the parameter to its default. This includes every deployment created from the earlier `examples/deployments/infrahub.yml` manifest, which set `replicas_task_worker: 1`. See [Migrating Replica Parameters](https://styrmin.pages.dev/docs/drivers/migrating-replica-parameters#deployments-created-from-the-earlier-example-manifest). ([#202](https://github.com/opsmill/styrmin/issues/202))
- Removed the `node_selector` setting from cluster and deployment configuration, and the `nodeSelector` field from the `UpdateClusterInput`, `UpdateDeploymentInput` and `DeploymentConfigInput` GraphQL inputs. Styrmin stored the value but never applied it to a pod. To place pods on nodes by label, set `scheduling.node_affinity` on the environment or the deployment; the [Node affinity](https://styrmin.pages.dev/docs/concepts-and-architecture/node-affinity) page shows how to convert a value such as `pool=apps`. There is no cluster-wide replacement, because Styrmin also ignores a cluster's `scheduling` value ([#482](https://github.com/opsmill/styrmin/issues/482)). `styrmin db migrate` deletes the stored values. ([#472](https://github.com/opsmill/styrmin/issues/472))
- Removed the `scheduling` setting from cluster configuration, the `scheduling` field from the `UpdateClusterInput` GraphQL input, and "Scheduling defaults" from the cluster page, which now says that scheduling is set on each environment or deployment. Styrmin stored the cluster value but never applied it to a pod. `createCluster`, `styrminctl clusters create`, `styrminctl clusters update` and `clusters.update()` in the Python SDK now refuse a cluster config that holds the `scheduling` key, whatever its value, `null` included: set scheduling on the environment or the deployment instead. `styrmin db migrate` deletes the stored values. ([#482](https://github.com/opsmill/styrmin/issues/482))

### Added

- Added `styrminctl deployments scale <deployment> <component> <count>` and `client.deployments.scale()` in the Python SDK, which set or, with `--clear` or `replicas=None`, remove the replica override of one component and keep every other override of the deployment. Added the server setting `STYRMIN_MAX_REPLICA_COUNT` (Helm value `styrmin.maxReplicaCount`, default 20): a new or changed replica override above it is rejected with `REPLICA_COUNT_ABOVE_MAXIMUM` before any task starts, while a stored count sent again unchanged is kept. The review dialog of the Edit configuration drawer now lists one line per replica change, for example `server: 3 → 1 pod`. The Upgrade Deployment dialog now shows a `RETIRED_PARAMETER_VALUE` rejection with the steps that fix it on the Settings tab, a button that opens that tab and clickable links to the guides, and links in its other error messages are clickable too. The SDK and `styrminctl` now reject a replica count that is not a whole number, such as `true` or `"3"`, before they send a request. ([#202](https://github.com/opsmill/styrmin/issues/202))
- Added replica overrides: a user can now set the replica count of one component of a deployment, a whole number from 1 to the server's maximum, in the Deploy form and the Edit configuration drawer, with `ComponentConfigInput.replicas` on `deploy`, `updateDeployment` and `updateDeploymentVersion` in the API and the SDK, and with `components[].replicas` in a `styrminctl deployments apply` manifest. Styrmin sets the count on `spec.replicas` of every `Deployment` and `StatefulSet` that matches the component's label selector after the Helm chart renders, so the component needs no component container and the driver needs no parameter. The count comes from the replica override, then from the driver default, then from the chart; a stopped component keeps its override and runs 0 pods until it is started, and the update task completes once the workloads report the new count of ready pods. A driver can declare a default count (`components.<name>.replicas`) and mark a component that must run a single pod with `singleton: true`, which fixes its count at 1; a driver that combines `singleton: true` with `replicas` above 1, or sets an invalid value, fails to load. The new `Deployment.componentReplicas` field in the API and the SDK reports each component's count, its source (`OVERRIDE`, `DRIVER_DEFAULT` or `CHART`), the stored override and whether it applies; the Component Overrides card on the Settings tab shows the same, `styrminctl deployments get` shows it in a new `replicas` column, and the Components tab of the driver page shows each component's default count and singleton flag (`ComponentConfig.replicas` and `ComponentConfig.singleton` in the API). Styrmin rejects a write before any task starts with `INVALID_REPLICA_COUNT` for a count below 1 (stop the component instead), with `SINGLETON_REPLICA_OVERRIDE` for a count above 1 on a singleton component, also on a change to a driver version that marks the component as singleton, and with `UNKNOWN_COMPONENT_REPLICA_OVERRIDE` for a new or changed count on a component that the driver version does not declare. An override on a component that a new driver version no longer declares is kept and not applied, and `styrminctl deployments apply` warns about it. The `simple-app` example driver moves to version 4, which marks `database` as a singleton component. ([#202](https://github.com/opsmill/styrmin/issues/202))
- Added loading an application driver from a driver directory of a git repository, so one repository can hold several drivers: `styrminctl drivers load-version --driver-directory`, `driver_directory` on `drivers.load_version()` in the Python SDK, the `driverDirectory` argument of `loadRemoteApplicationDriverVersion`, the `driverDirectory` field of `ApplicationDriverVersion` and the "Driver directory (optional)" field of the "Load a driver" drawer. The driver version's Overview tab, the drivers list, the deploy form, the Upgrade dialog and the version picker of the driver page show the driver directory, and the Upgrade dialog warns when "Latest (auto)" can move a deployment to another driver directory of a driver with the same name. The driver's actions run from the driver directory and can import only modules inside it. A driver directory that starts with `/`, contains a `..` segment, a backslash, `{`, `}` or a control character, or is longer than 255 characters is refused. A reload after any commit to the repository creates a new driver version, even when the driver directory did not change. A load with a driver directory needs an upgraded Styrmin server; loads without one keep working against older servers. See [Loading a Driver](https://styrmin.pages.dev/docs/drivers/loading-drivers#loading-a-driver-from-a-driver-directory). ([#517](https://github.com/opsmill/styrmin/issues/517))

### Changed

- Changed the `infrahub` and `infrahub-enterprise` example drivers to versions 5 and 4, which remove the `replicas_server` and `replicas_task_worker` parameters: `server` and `task-worker` now have driver defaults of 1 and 2 replicas, the defaults of the old parameters, and `database`, `task-manager-db` and `cache` are singleton components. - Fixed Velero backup-repository maintenance, which had never run in any Styrmin install: Velero resolves its own Deployment by the hardcoded name `velero` to build the kopia maintenance Job, but the `velero` subchart named it `<release>-velero`, so every cycle failed with `Deployment.apps "velero" not found`, kopia never pruned, and the data behind expired backups was never reclaimed from the bucket. `helm/styrmin/values.yaml` now pins `velero.fullnameOverride: velero`. **Upgrading:** the Velero Deployment, Service, ServiceAccount, and ConfigMaps are renamed, so `helm upgrade` replaces them and the Velero pod restarts once; update anything referring to the old names (`deployment/<release>-velero`, dashboards, scrape configs) to `velero`. The PVC-patch ConfigMap is now `velero-restore-pvc-patch`; Restores created before the upgrade keep pointing at the old name and cannot be re-driven, but Restores are one-shot objects and new ones are unaffected. Helm creates the renamed Deployment before it deletes the old one, so two Velero servers overlap for a few seconds; do not upgrade while a backup or restore is in flight.
- Fixed Velero's idle log volume, now roughly 5x quieter: `--backup-sync-period` and `--store-validation-frequency` default to `5m` instead of Velero's 1m. Each cycle spawned and killed an object-store plugin process whose teardown logs a spurious error ([velero#7892](https://github.com/vmware-tanzu/velero/issues/7892)), so the default cadence buried real backup logs under ~7 noise lines a minute per BackupStorageLocation. Styrmin names the BSL on every backup and tracks backup state in its own database, so neither loop was load-bearing.
