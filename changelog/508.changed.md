Changed how Styrmin stores a deployment reference (`deploymentRef`) in a pod affinity or pod anti-affinity term: `deploy`, `updateDeployment`, `updateDeploymentVersion`, `createEnvironment`, `updateEnvironment` and `styrminctl deployments apply` now replace a `deploymentName` with the id of the deployment that has that name before they save the config, and reading the config back gives `deployment_id` only. A write whose term names, by name or by id, a deployment that the environment does not have or a deleted deployment is now refused with `VALIDATION_ERROR` and the term's path, and saves nothing; before, a term in an environment's config was checked only at the next reconcile. `createEnvironment` and `styrminctl environments create -c` therefore refuse every term that names a deployment, because a new environment has no deployment. Deleting a deployment gives no warning about the terms that name it: every later update of the deployments that such a term applies to, and their config fan-out redeploys, now fail with the term's path, the deleted deployment's last name and `deleted: true` until the term is written again, for example by re-applying the manifest once a deployment with the same name exists again; before, such a term gave a selector that matched no pod. A term that a deeper level discards with `replace: true` is now resolved too, so it can fail a reconcile. Re-applying an unchanged manifest whose terms give names still starts no reconcile. A term that a driver version's component definition gives by name is looked up each time the definitions are copied, so after the named deployment is renamed, a `deploy` with that driver version, an `updateDeploymentVersion` to such a driver version and a clone of a deployment that uses it are refused. `cloneEnvironment` now points the copied terms at the counterpart deployments, and refuses with `VALIDATION_ERROR`, before it creates a clone record or a backup, a request whose copied terms name a deployment that the clone does not copy, including an empty selection (a clone of the configuration only) when the environment's config has such a term; `extensions.deployments` lists each such deployment and the paths of the terms that name it. During a clone, a counterpart whose config has a term that names a deployment that could not be cloned now fails with the reason `an affinity term names deployment <name>, which was not cloned`, and a clone whose new environment's config names that deployment fails with the `referenced_deployment_not_cloned` event. `cloneEnvironment` also refuses at request time a source environment config that no longer validates, which used to fail the clone. See [Choosing which deployments come along](https://styrmin.pages.dev/docs/concepts-and-architecture/backups-and-restores#choosing-which-deployments-come-along).
