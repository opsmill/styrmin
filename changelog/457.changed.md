Changed how container `command` and `args` overrides reach pods: Styrmin now applies them after the Helm chart renders, to the component container the driver declares (`components.<name>.container`), together with env vars and image overrides, so a driver no longer passes them to the chart in `values.j2.yml`. An override replaces the whole `command` or `args` list, a field without an override keeps the value the chart renders, clearing an override brings back the chart's `command` and `args`, and overrides no longer reach chart Jobs, init containers or other containers in the pod. The `server` and `task-worker` components of the `infrahub` and `infrahub-enterprise` example drivers now accept `command`, and the `simple-app`, `infrahub` and `infrahub-enterprise` example drivers move to versions 3, 4 and 3. Adding or changing `command` or `args` on a component without a component container is now rejected with `COMPONENT_CONTAINER_NOT_DECLARED` (metadata `override` set to `command` or `args`); removing a stored value, or sending the same value again, is still accepted. The deployment's Configuration editor hides the Command and Args editors for such a component, shows stored values read-only as JSON lists, marked "not applied", with a remove button, and explains that the component accepts no overrides instead of offering "Add override"; the new `ComponentContainerOverrides.isApplicable` field in the API and the SDK reports whether a stored override applies. The Command and Args editors explain what they replace and what happens with no rows, warn about an empty command element, and name each input for screen readers. The Component Overrides card on the Configuration tab now lists the stored `command` and `args` of each component as JSON lists, with an "applied" or "not applied" badge, and lists every block stored on a component the driver no longer declares, not only image overrides. `styrminctl deployments apply` now also warns on stderr about `command` and `args` that it stores but that the driver version does not apply; it prints one warning per component that names the kinds of override and says to remove them from the manifest or to load a driver version that declares a component container for the component, and the SDK lists the kinds per component in the new `ApplyOutcome.inapplicable_overrides`, next to `ApplyOutcome.inapplicable_components`.
