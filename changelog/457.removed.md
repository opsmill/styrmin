Removed the `component_command` and `component_args` driver template filters. A driver `values.j2.yml` that still calls either one now fails rendering with `RETIRED_TEMPLATE_FILTER` and an error that names the [migration guide](https://styrmin.pages.dev/docs/drivers/migrating-container-overrides), also when no override is set, so a deployment pinned to an unmigrated driver version fails on its next change until it moves to a migrated driver version; its pods keep running meanwhile. Removed `spec.container_overrides` from the driver specification file (a `driver.styrmin.yml` that still contains it fails to load), from the stored driver version (a database migration drops the column) and from the API and SDK: `ApplicationDriverVersion.containerOverrides`, the `DriverContainerOverrideDoc` type, the SDK's `get_driver_container_override_docs` method and the `DRIVER_CONTAINER_OVERRIDE_DOC_COMPONENT_MISMATCH` error code. Review the stored `command` and `args` overrides of your deployments before you move them to a migrated driver version: Styrmin now applies them to every component with a component container, so values that a driver template did not pass to the chart, such as `command` on the infrahub `server`, reach the pods for the first time, and on a driver whose template never called the filters they apply from the deployment's next change.
