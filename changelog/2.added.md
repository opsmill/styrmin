Added steps and failure causes to tasks, backups and restores. Each task on the deployment page lists its steps in order (planning the changes, each hook mode that runs, writing the StyrminDeployment resource, and the operator phases from network policies and secrets to the wait for readiness) with status, duration, attempts and the error of each failed attempt; the HelmRelease step shows FluxCD's current reason, FluxCD rollbacks and the pods that are not ready, and a failed command run by an action or by `runJob` keeps the end of its output (the last 200 lines, at most 64 KiB), which every signed-in user can read, so action commands must not print secrets. Each task shows a result calculated from its steps and from the tasks its hook started (`RUNNING`, `FAILED`, `SUCCEEDED`, or `SUPERSEDED` with a link to the task that interrupted it), the page refreshes every 10 seconds and says when the agent has sent no report for more than 60 seconds, restores show their three steps and backups one step per component. Available as `Task.steps`, `Task.result`, `Task.startedBy`, `Task.startedTasks`, `Backup.steps`, `Restore.steps` and `Query.step` in the API; `tasks.failed_step()` and the `FailedStep`, `TaskStep`, `StepStatus`, `StepKind` and `TaskResult` models in the SDK; a result column, a steps table and a started-tasks table in `styrminctl tasks get`; and the failed step's name and error in the `failed` line of `styrminctl deployments apply --wait`. The agent's role can now read Velero `PodVolumeBackup` objects. Tasks, backups and restores from before this release show no steps.
