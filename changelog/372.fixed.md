Fixed the actions of drivers loaded with `styrminctl drivers load-local-version`, which never ran: a deployment created or upgraded from such a driver now runs its setup and upgrade actions, and a hook whose declared action has no registered flow now fails with an error that tells you to load the driver again, instead of being skipped. The Styrmin agent runs these actions from the same path as the server, so a driver that only the server container holds now fails its actions with an error that names the path and the agent pod and says how to put the driver there; the errors no longer name an image, because an action's `image:` has no effect. Load your local drivers again after you upgrade, to register their actions. Deployments created from local drivers before this fix never ran their setup actions, and Styrmin does not run them now. A load from a local directory of a driver that declares actions is now refused when the path is relative or when an action's `location` is in another file than `actions.py`, and a load from git or from a local directory is refused when the driver declares two actions for one hook and mode; the check before each action covers `actions.py` but not the modules that it imports. When the flow run of an action crashes, its hook step now shows the first `ERROR` log line of that run, with the action's API token and common forms of secrets replaced by `<redacted>`; every signed-in user who can read the task can read it, so actions must not write secrets to their logs. Deleting a deployment whose create failed before its `StyrminDeployment` was written, for example at the setup pre-hook, now deletes it instead of returning "An internal error occurred"; while a change of such a deployment is still applied, the delete is refused with a message that names the deployment and says to delete it again when its status is running or failed. When an upgrade fails because an upgrade action has no registered flow, the deployment keeps its version, and `styrminctl deployments update-version` and `styrminctl deployments apply` print the error and exit with code 1, `apply --wait` included. A second `execute_commands` call on the same deployment, for example in the next upgrade with the bundled `simple-app` or `infrahub` drivers, now deletes the Job that the earlier call left, once that Job has ended, and runs its commands, instead of failing because a Job of that name already exists; the hook step names the deleted Job. A Job of that name that is still running, for example the migration Job of another upgrade of the same deployment, is never deleted: the action fails and tells you to wait for the Job to end and request the change again.
